# Findings

## Workspace package layout (established by packages/db, reuse verbatim)

Every leaf workspace package carries five files and nothing else at setup time:

  <pkg>/package.json          name @marcos-corp/<x>, private, type module,
                              exports/main/types -> ./src/index.ts,
                              engines.node >=22, author + Apache-2.0 to match root
  <pkg>/tsconfig.json         extends ../../tsconfig.base.json; adds lib ES2022,
                              module ESNext, noUnusedLocals/Parameters,
                              noImplicitReturns/This, noFallthroughCasesInSwitch;
                              include ["src", "*.ts"];
                              exclude ["node_modules","dist",".tmp","drizzle","**/*.test.ts"]
  <pkg>/eslint.config.mjs     `import baseConfig from '../../eslint.base.mjs'`,
                              exports [ {ignores:[...]}, ...baseConfig ]
  <pkg>/vitest.config.ts      environment node, include ['src/**/*.test.ts']
  <pkg>/src/index.ts          module placeholder (`export {};`) until real exports land

Leaf scripts are exactly: `lint`: `eslint .`, `check-types`: `tsc --noEmit`,
`test`: `vitest run`. All three run from the package directory, so each picks up
its own leaf config with no extra flags.

## Tooling devDependencies stay at the ROOT, not in leaf packages

eslint, typescript, vitest, typescript-eslint, globals, jsonc-eslint-parser etc.
are already root devDependencies and hoist into the top-level node_modules, so
`bun run lint|check-types|test` inside a package resolves them without the
package declaring anything. Do NOT re-declare them per package — that is version
drift for no gain. Only declare a package's own *runtime* deps (drizzle-orm,
@sinclair/typebox, express, ...). The ported reference package under
.claude/worktrees/ duplicates devDeps because it was a standalone template; do
not copy that part of it.

## `--passWithNoTests` is temporary debt, not the convention

A package created before its first suite exists needs `vitest run
--passWithNoTests`, otherwise vitest exits 1 on "No test files found" and the
plan's "test:all exits 0 across all eight packages" task cannot pass. The flag is
recorded in that package's vitest.config.ts comment. **Drop the flag in the same
task that adds the package's first test file** — left in permanently, a deleted
suite goes green and unnoticed.

## bun does NOT symlink a workspace package into node_modules until something depends on it

`node_modules/@marcos-corp/` does not exist even after `bun install` registers
`packages/db` in bun.lock (verified: the ported reference monorepo has no
`node_modules/@ar` either, same setup). Consequence for any task wiring a
cross-package import: the consumer must declare the dependency in its own
package.json, or both `import/no-unresolved` and tsc will fail. Registering the
workspace is not enough.

## Root eslint leaf ignores `packages/**` but NOT `apps/**` or `services/**`

`eslint.config.mjs` at the root ignores only `packages/**`. When `apps/*` and
`services/*` land, root `bun run lint` will lint them with the ROOT config
(whose import resolver points at `./tsconfig.json`, which excludes them), and
`lint:all` will then lint them a second time through their own leaf config. The
task that creates the first app or service must add `'apps/**'` and
`'services/**'` to the root ignores block.

## Prove a green gate actually read the files

`eslint .` exiting 0 proves nothing on its own. Two cheap checks used here:
  bunx eslint . -f json | ...        -> count + names of files actually linted
  bunx tsc --noEmit --listFiles      -> the exact file set tsc type-checked
and a throwaway violation file (e.g. a double-quoted string) to confirm the gate
reddens before deleting it. Worth repeating for each new package.

## Shell traps hit in this repo

- The Bash tool's cwd PERSISTS between calls. A `cd packages/db` in one call
  makes a relative `cd packages/db` in the next call fail. Use absolute paths.
- The shell is zsh: `${PIPESTATUS[1]}` after a pipe reads the WRONG element and
  a trailing `; echo $?` after a pipe reports the exit of the LAST stage (often
  `tail`/`ls`), not the command under test. Capture with
  `cmd > /tmp/x.log 2>&1; echo "EXIT=$?"` when the exit code is the evidence.

## Verification order (from AGENTS.md), all four confirmed green with packages/db

  bun run lint && bun run check-types && bun run test && bun run gate:control-bytes

`gate:control-bytes` scans **tracked** files only, so a new package is outside
its scope until it is committed — run it once more after the commit.

## Cloning the packages/db layout: two bits are db-specific, drop them

`packages/db` is the template for every remaining leaf, but two of its lines
describe drizzle artifacts and mean nothing anywhere else:

  tsconfig.json   exclude ["...", "drizzle", ...]   <- drop outside packages/db
  eslint.config.mjs  { ignores: ['drizzle/**', ...] } <- drop outside packages/db

Keep `.tmp/**` in both; it is generic. Copying `drizzle` into a package that
will never hold a migration reads as cargo-cult to the reviewer. Everything
else in the five-file layout transfers verbatim.

## What each leaf gate actually reads (measured, not assumed)

In a leaf package, `eslint .` and `tsc --noEmit` cover DIFFERENT file sets:

  eslint .        5 files: eslint.config.mjs, vitest.config.ts, src/index.ts,
                  AND package.json + tsconfig.json (the jsonc plugin in
                  eslint.base.mjs makes both JSON configs real lint targets)
  tsc --noEmit    2 files: src/index.ts, vitest.config.ts
                  eslint.config.mjs is NOT type-checked (.mjs, allowJs off)

Two consequences: a badly formatted package.json fails `lint`, not
`check-types`; and a type error inside a leaf `eslint.config.mjs` is invisible
to every gate in the verification order.

## bun uses the ISOLATED linker: a leaf's runtime deps are NOT hoisted to root

The devDependency note above is true only for the ROOT. A dep declared by a
leaf is symlinked into `packages/<pkg>/node_modules/` and never appears in the
top-level `node_modules/` (real copies sit under `node_modules/.bun/`).
Verified with @sinclair/typebox and @ts-rest/core.

- Leaf runtime deps resolve for `lint`/`check-types` only because those scripts
  run FROM the package dir. Never "fix" a leaf import by adding the dep at root.
- `ls node_modules | grep <dep>` at the root is a false-negative install check;
  read `packages/<pkg>/node_modules/`, or `node_modules/.bun/`, which carries
  the resolved version in the directory name.

## @ts-rest/core's optional zod peer is a LIE at runtime: the ESM build imports it

`@ts-rest/core@3.52.1` (the `latest` tag; there is no v4) declares
`peerDependencies.zod: ^3.22.3` and marks it **optional** in
`peerDependenciesMeta`, which reads as "zod is only needed if you author in
zod". That is true for `tsc` and false for `node`: line 1 of
`index.esm.mjs` is a bare `import { z } from 'zod'`, evaluated at module load.

So **any package that imports `@ts-rest/core` at runtime must declare `zod`
itself** — `initContract()`, `isAppRoute`, `ContractNoBody` and
`ContractPlainTypeRuntimeSymbol` are all unreachable without it. Under the
isolated linker nothing hoists, so it is per package. The failure is
`Error: Cannot find package 'zod' imported from .../@ts-rest/core/index.esm.mjs`,
at import time, so a whole test file reports zero tests rather than one
failure.

Two consequences worth carrying:

- `packages/contracts-*` will each need `zod` declared even though spec 2.4
  forbids authoring contract schemas in it. That is not a violation — the rule
  is about what a contract *publishes*, and `docs/governance.md` already scopes
  Zod as "banned inside `packages/contracts-*`" in the authoring sense. Say so
  explicitly wherever a reviewer will see the dependency, or it reads as one.
- The root `overrides.zod: 4.5.1` wins over ts-rest's `^3.22.3` peer, and
  ts-rest 3.52.1 loads and runs fine against zod 4.5.1 for the contract-shape
  surface this repo uses (verified: 251 cases green). `bun install` prints no
  peer warning either way.

Still true, and still worth doing: check `npm view <pkg> peerDependenciesMeta`
before working around a peer warning. Just do not conclude from `optional` that
the package can be *imported* without it — read the built entrypoint.

## Prove a new dependency resolves, with a negative control

Gates stay green whether or not a declared dep is importable, so declaring one
and re-running them proves nothing. Per package that adds a runtime dep:
write `src/__probe.ts` importing it and using a real export; `bunx tsc
--noEmit` and `bunx eslint src/__probe.ts` must both exit 0 (eslint's
`import/no-unresolved` covers what tsc does not); then break it deliberately
(type error, then an import of a nonexistent package) and confirm each gate
exits non-zero; then delete the probe and re-run. Without the negative control
a green run is indistinguishable from a gate that read nothing.

## Two deltas specific to `packages/contracts-*`

- Leaf `eslint.config.mjs` must ignore `openapi/**`: those packages commit
  emitted `openapi/openapi.json` and `openapi/published/<version>.json`, and
  the jsonc plugin in `eslint.base.mjs` makes every committed .json a lint
  target otherwise.
- The manifest `version` is API surface, not bookkeeping — consumers pin it
  exactly with no range specifier (spec 2.2) and a gate enforces that, so
  bumping it is the reviewable event. The packages still stay `private: true`;
  "published" here means the committed OpenAPI document, never an npm registry.

## For a "mirror package X" task, diff the configs instead of re-reading them

Several plan tasks say "mirroring the <other> package configuration"
(contracts-service-b, service-b, web-a/web-b). After writing the new leaf, run
`diff <template>/<file> <new>/<file>` for each of package.json, tsconfig.json,
eslint.config.mjs and vitest.config.ts. A faithful mirror produces only the
name / display / description lines; anything else in the diff is an unintended
delta. This is stronger than re-reading each file, and it catches the reverse
failure too — a template-specific line copied where it does not belong (see the
drizzle-exclude note above).

## The root eslint ignores block is now closed over all three workspace globs

Confirmed by measurement, not assumption: with `services/` present and only
`packages/**` ignored, root `eslint .` read 32 files including all five
service leaf files; after adding `'apps/**'` and `'services/**'` it read 27 and
none under apps/ or services/. The root `eslint.config.mjs` ignores block now
lists all three globs declared in `package.json` workspaces, so no later
`apps/*` or `services/*` package has to touch it again. Root `tsconfig.json`
never needed the same fix — its `include` is `["tools", "*.ts", "*.mjs"]`, so
leaf packages were already outside it.

## ts-rest v3 pins Express 4, and its express peer is NOT optional

`@ts-rest/express@3.52.1` (the `latest` tag; 3.53.x is alpha/rc only) declares
`peerDependencies: { "@ts-rest/core": "~3.52.0", "express": "^4.0.0", "zod":
"^3.22.3" }` with **only zod** marked optional. Express 5.2.1 is `latest` on npm
and does not satisfy `^4.0.0`. Any service in this repo therefore takes
`express@^4.22.2` with `@types/express@^4.17.25`, and must also declare
`@ts-rest/core` itself — a non-optional peer does not get resolved for you under
bun's isolated linker. `bun install` printed no peer warnings with that set,
which is the check worth reading.

`@types/express` belongs in the **leaf** devDependencies, not the root: it is
package-specific typing rather than shared tooling, and the isolated linker
requires it to resolve from the package directory. That is the exception to the
"tooling devDeps stay at the root" note above — the rule is about *shared*
tooling, not about the `devDependencies` field.

Unrelated aside worth knowing: `@ts-rest/express`'s .d.ts references
`z.ZodObject` even though zod is not installed. `skipLibCheck: true` in
`tsconfig.base.json` is what keeps that from failing `check-types`.

## Proving a `dev` script, which by design never exits

`bun --watch <entry>` stays resident, so `bun run dev; echo $?` hangs rather
than reporting. Two cheap readings instead:
  bun src/index.ts                          -> entrypoint executes, exit 0
  bun run dev (backgrounded) + pgrep -fl    -> the script resolves and the
                                               watcher is actually running
then `pkill -f 'bun --watch src/index.ts'`. The backgrounded job reports exit
143 (SIGTERM) afterwards; that is the kill, not a failure.

## A service leaf carries a `dev` script; the entrypoint is src/index.ts

`src/index.ts` is already the package's `exports`/`main`/`types`, so pointing
`dev` at it keeps one entrypoint and makes the script runnable from the day the
package is created rather than pointing at a `server.ts` that lands tasks later.
When `server.ts` arrives, wire it in through `src/index.ts` instead of
repointing the script.

## `bun install` printing "no changes" still registers a new workspace package

Adding a leaf whose runtime deps are already in the lockfile (a mirror of an
existing package) makes `bun install` print `Checked N installs across M
packages (no changes)`. That line describes the *dependency graph*, not the
workspace set, and reads as a no-op when it is not one — the same run wrote
`Saved lockfile`, added the `services/<pkg>` / `@marcos-corp/<pkg>` entries to
`bun.lock`, and created the leaf's own `node_modules/` symlinks. Do not re-run
install or start debugging on the strength of "no changes"; read the two things
that actually answer it:

  grep '<pkg>' bun.lock              -> workspace entry + resolution line
  ls <pkg>/node_modules              -> the isolated linker's per-leaf symlinks

## A dependency-free leaf gets NO `<pkg>/node_modules` at all

Refines the two notes above about the isolated linker. `ls <pkg>/node_modules`
only answers "did the leaf's own runtime deps link"; for a leaf that declares
none (apps/web-a, apps/web-b, packages/db, packages/contract-tooling) the
directory is never created, so its absence reads as a failed install when
nothing is wrong. To confirm a workspace registered, read `bun.lock` — both the
`"<glob>/<pkg>": { "name": "@marcos-corp/<pkg>" }` workspace entry and the
`"@marcos-corp/<pkg>": ["@marcos-corp/<pkg>@workspace:<glob>/<pkg>"]`
resolution line — and confirm the package appears in the
`bun run --filter '@marcos-corp/*' <script>` output. Such a leaf still lints,
type-checks and tests green because every tool it uses is a hoisted root
devDependency.

## `bun run --filter` DOES propagate a leaf failure — verified, not assumed

A green `bun run <gate>:all` is otherwise indistinguishable from a `--filter`
that swallows leaf exit codes, and every "all N packages exit 0" claim in this
plan rests on it. Measured by planting one violation in a single leaf and
reading the aggregate exit:

  lint        double-quoted string   -> leaf 1, aggregate 1
  check-types `number` into `string` -> leaf 2, aggregate 2  (tsc's 2 shows through)
  test        `expect(1).toBe(2)`    -> leaf 1, aggregate 1

Two properties worth knowing beyond the propagation itself:

- It does **not** short-circuit. The other seven leaves still ran and still
  printed `Exited with code 0` in the same failing capture, so the presence of
  green lines next to a red one is normal output, not a partial run.
- The aggregate takes the leaf's own code, so a non-1 exit (tsc's 2) is a real
  reading, not a harness artifact. Test for non-zero, never for `-eq 1`.
- Leaf order is **nondeterministic** between runs. Never read the Nth line
  positionally; `grep -oE '@marcos-corp/[a-z-]+ <script>: Exited with code 0'`
  and `sort` before comparing two captures or counting the package set.

Re-do the plant/restore control whenever a new gate script is added to the root
`*:all` fan-out. It costs three runs and is the only thing separating "eight
packages pass" from "the filter reported nothing eight times".

## The `packageManager` pin is NOT enforced by bun

`package.json` pins `bun@1.3.9`; `bun install` ran as **1.3.14** and said
nothing. Unlike corepack-managed pnpm/yarn, bun does not refuse or self-switch
on a mismatched `packageManager` field, so that line documents intent only. Read
`bun --version` when a version-sensitive behaviour is in question rather than
trusting the manifest, and expect CI's bun to differ from the local one unless
the workflow pins it explicitly with `oven-sh/setup-bun`.

## A green `test:all` says almost nothing about the leaves — read the leaf line

Extends the `--passWithNoTests` note above with the measured state. Seven of
the eight leaves still carry the flag and still print `No test files found,
exiting with code 0`; only `packages/contract-tooling` has dropped it, and its
20 cases are the only leaf coverage in the repo. Every other passing test
belongs to the ROOT suite over `tools/`. So `test:all` exiting 0 is a statement
about the root, one real leaf and seven no-ops. Any task claiming coverage from
a leaf must read that leaf's own `Test Files N passed` line, not the aggregate
exit — and must drop that leaf's `--passWithNoTests` in the same commit that
adds its first suite.

## No lint gate reads YAML or extensionless files -- only the byte gate does

`eslint.base.mjs` declares `files:` for js/mjs/cjs/ts/tsx/jsx/md/json and
nothing else. So `.github/CODEOWNERS`, `.github/workflows/*.yml`,
`docker/compose.yaml` and `packages/contract-tooling/rulesets/*.yaml` are
outside `lint`, `lint:all` and `check-types` entirely. The only gate that ever
opens them is `gate:control-bytes`, and that one scans **tracked** files, so a
brand-new YAML or extensionless config is read by nothing at all until it is
committed. A green four-gate run after adding one is not evidence the file is
well-formed -- whatever validity check that file deserves has to be written or
run by hand in the same task.

## A path-pattern config that matches nothing fails silently -- check it, with a control

CODEOWNERS, workflow `paths:` filters and ruleset globs all share the failure
mode: a typo'd or wrong-case path is not an error, it just owns/triggers
nothing, and the file still reads as correct. Cheap check that catches it --
for every non-comment rule, count the tracked files the pattern actually
matches:

  grep -vE '^\s*(#|$)' <file> | while read -r pat rest; do
    printf '%-34s %s\n' "$pat" "$(git ls-files -- "${pat#/}" | wc -l)"
  done

Pair it with a negative control in the same run (a nonexistent sibling, a
misspelling, a case variant) or a check that reports a nonzero count for
everything is indistinguishable from one that works. Both were run for
`.github/CODEOWNERS`: 8 rules x 5 tracked files each, 0 for all three controls.

## CODEOWNERS semantics that the plan's prose does not imply

Relevant to `docs/ownership.md`, the CI `paths:` filters and acceptance script
05, all of which reason about who approves what:

- **Last match wins.** Ownership does NOT accumulate across matching lines the
  way .gitignore rules do; the final matching rule is the only one that applies.
  List general patterns before specific ones.
- **A leading `/` anchors to the repo root.** `packages/db/` without it also
  matches any nested `packages/db/` deeper in the tree.
- **Two owners on one line means EITHER may approve**, not both. To require two
  approvals you need the PR to touch two paths with disjoint owner sets.
- **An unresolvable handle matches nobody, with no error.** The org/team form
  `@marcos-corp/team-a` cannot resolve on a user-account repo like this one, so
  every rule here is documentation until the handles are swapped (tracked in
  `.plans/PREREQUISITES-*.md`) and branch protection on `main` requires
  code-owner review.

## Tracked markdown IS a lint target -- `docs/**` is not ignored anywhere

Refines the "no lint gate reads YAML or extensionless files" note above: the
opposite is true for `.md`. `eslint.base.mjs` declares a `files: ['**/*.md']`
block extending `markdown/recommended`, and the root `eslint.config.mjs`
ignores block lists only the three workspace globs plus `.claude/`, `.plans/`,
`.specs/`, `.tmp/`, `.docs/` -- **not** `docs/`. So every file added under
`docs/` is read by root `bun run lint`, and by `gate:control-bytes` once
committed.

Measured, with negative controls, when `docs/ownership.md` landed:
  bunx eslint . -f json | ...      -> 28 files, docs/ownership.md among them
  `#BadHeading` planted            -> exit 1, markdown/no-missing-atx-heading-space
  literal U+200B planted           -> exit 1, house/no-unsafe-unicode
  restored                         -> exit 0
  gate:control-bytes               -> 93 files pre-commit, 94 after

Rules that actually bite prose: `no-missing-atx-heading-space`,
`no-duplicate-headings`, `no-multiple-h1`, `table-column-count` (every row of a
table needs the same cell count). `markdown/no-missing-label-refs` is turned
off in `eslint.base.mjs`, so bare `[bracketed]` text is safe.

Related skills for the remaining `docs/*` tasks:
`markdown-link-check-strip-code-regions` (strip fences/spans before scanning
for links) and `wrapped-prose-edit-safety` (span edits never reflow the rest of
a hand-wrapped paragraph).

## Width checks with awk count BYTES, so `--` and section signs read as over-long

Prose convention in this repo's authored docs (AGENTS.md, CLAUDE.md, `.specs/`,
`.plans/`) is hand-wrapped at 80 columns; tables and long link targets are
allowed past it. README.md and PRESENTATION.md are unwrapped and are not the
model to copy.

`awk '{ if (length($0) > 80) ... }'` on macOS counts bytes, not characters. An
em dash costs 3 bytes and a section sign 2, so a correctly wrapped 80-character
line reports as 85 and reads as a violation that is not there. Subtract the
multibyte characters before believing the number, or measure with
`python3 -c "print(max(len(l) for l in open(p)))"`.

Neither character is banned -- `house/no-unsafe-unicode` flags only C0/DEL,
BiDi overrides, zero-width and default-ignorable code points, and U+2028/9. The
existing docs use both.

## Relative links out of `docs/` resolve, and are worth checking with a control

A link from `docs/x.md` to a repo-root path needs the `../` prefix
(`../.github/CODEOWNERS`), and nothing in the four-gate verification order
opens it -- a dead link is green. Cheap check, run from the repo root:

  grep -oE '\]\(([^)]+)\)' docs/x.md | sed 's/](//; s/)$//' | while read -r l; do
    python3 -c "import os,sys; p=os.path.normpath('docs/'+sys.argv[1]); \
      print(('OK      ' if os.path.exists(p) else 'MISSING ')+p)" "$l"
  done

Pair it with a deliberately misspelled target in the same run, or a checker
that reports OK for everything is indistinguishable from one that works.

## Docs that describe not-yet-built code: bound the staleness, don't scatter it

Every remaining `docs/*` task writes prose about gates, scripts and workflows
that land in later stages. Two rules keep those docs from being silently
falsified by the commit that builds the thing they describe:

- **Reference a file that does not exist yet in backticks, never as a markdown
  link.** `docs/ci.md` in backticks is a forward pointer; `[x](ci.md)` is a dead
  link that the four-gate order will never catch (nothing in lint, check-types,
  test or the byte gate opens a link target).
- **Confine "not true yet" claims to one clearly-titled section, and phrase each
  so it is still true at the end of the plan.** "The CODEOWNERS handles are
  placeholders" and "the 13-month retention is a requirement this PoC does not
  satisfy" survive every later stage. "These gates do not exist yet" does not,
  and goes stale in a file nobody re-reads. See `stale-prose-sweep-on-commit`.

## Where the governance facts live, so docs tasks stop re-deriving them

`docs/governance.md` is now the single place the spec §10 decisions are recorded
as resolved (TypeBox + ts-rest in contract packages, Zod everywhere internal but
never in `packages/contracts-*`, `client_id` issued manually with a named owner,
contract packages versioned independently). Later docs, README sections and
package `AGENTS.md` files should link to it rather than restating the rationale.

The spec sections each doc task draws from, since they are not adjacent in the
file: §4 tier-to-gate table, §7 out-of-scope triggers, §8 gate order + house
rules, §9 acceptance criteria, §10 open decisions. `PRESENTATION.md` lines 18-56
hold the original tier definitions that §4 restates.

## Checking a markdown table before lint does: count cells per row

`markdown/table-column-count` fires on a row whose cell count differs from the
header, and a hand-aligned table is easy to get wrong mid-edit. Cheaper than
reading it: strip the leading/trailing pipe, split on `|`, and assert one
distinct count per contiguous table block. Run it together with the h1-count and
duplicate-heading checks — all three are pure text and need no tooling.

## vacuum is Spectral-*ruleset* compatible, not Spectral-*function* compatible

Measured on vacuum 0.30.3 while authoring
`packages/contract-tooling/rulesets/house.spectral.yaml`. Each item below turns
a rule into a silent pass: it loads, it counts toward "containing N rules", and
it reports nothing, ever.

- The `schema` function only validates a **`field`**, never the `given` node.
  Spectral's node-level `then: {function: schema}` with no `field` checks
  nothing. This is the easiest way to ship a dead rule.
- With a `field`, `schema` still passes when that field is **absent** unless
  `forceValidation: true` is set.
- `functionOptions` rejects Spectral's `allErrors`, and surfaces the rejection
  as a *violation on the spec* ("property 'allErrors' is not a valid property
  for 'schema'") rather than as a ruleset load error.
- `message:` is **not** interpolated -- `{{path}}` / `{{property}}` / `{{error}}`
  print literally. Reported text is `"<description>: <function message>"`, so
  write `description` to read as the first half of that sentence and omit
  `message`.
- `@property` is unsupported in filters, so "every 4xx/5xx response" must be an
  explicit union: `responses[400,401,403,404,409,422,500]`.

What does work and is worth reaching for: filters support `!`, `&&`, `||`, `==`
and nested member access (`$..[?(@.items && !@.items.type)].items`); `then`
accepts an **array** of entries against one `given`; the schema function
supports `patternProperties`, `contains`, `const` and `not`. Prefer the
given-as-predicate idiom -- select only the offending nodes, then assert
something that cannot hold -- over a node-level schema check: it yields real
document paths and messages like "`type` must be defined".

## vacuum resolves $ref before running a rule, which changes what a rule can see

Default execution is against the **resolved** document, so a `$ref` string is
already gone; a rule reasoning about one needs `resolved: false` on that rule.
Two consequences past that:

- One violation can be reported **twice** -- once at its real path, once at the
  resolved copy, where vacuum cannot render a path and prints the raw filter
  (`[?(@.type == 'object')]`) instead. Assert the rule **code**, never a finding
  count of exactly 1.
- `range.start.line` is correct even when the path is that raw filter, so it is
  the field to point a human at.

## Reading vacuum from code: `lint` has no JSON, and `spectral-report` has THREE outcomes

`vacuum lint` exits 0 clean / 1 at error severity but has no JSON flag. The
machine-readable path is `vacuum spectral-report -r <ruleset> -o <spec>`, which
writes a bare JSON array to stdout with no banner and **exits 0 whether or not
there are findings**. Anything shelling out to it must derive pass/fail from the
parsed array, not from the exit code. Finding fields: `code` (rule id), `path`
(array), `message`, `severity`, `range.start.line`. Both YAML and JSON specs
work, so the committed `openapi/*.json` artifacts lint directly.

The exit-0 rule holds only while the spec **parses**. There is a third outcome,
and it is the one that breaks a naive wrapper: on an unparseable spec vacuum
exits **2** and writes an ANSI-coloured `✗ Failed to parse specification '<path>'`
to **stdout**, not stderr. So `JSON.parse(stdout)` throws rather than returning
an empty finding list, and the throw does not name the spec unless the raw
stdout is kept. Any `lintSpec` has to branch on all three: exit 2 (unparseable,
report the path), exit 0 with `[]` (clean), exit 0 with findings (fail). Note
the blob carries ESC bytes, so never tee it into a tracked file -- that is
exactly what `gate:control-bytes` and `house/no-unsafe-unicode` reject.

vacuum is a documented prerequisite and is **not** installed on this machine.
For local verification without touching the repo:
`npm install --prefix /tmp/vacuum-probe @quobix/vacuum@0.30.3`, then prepend
`/tmp/vacuum-probe/node_modules/.bin` to PATH. Pin the version CI installs.

## Prove a lint rule is live: one violating document per rule, and per leg

A ruleset that loads and reports nothing looks exactly like a correct one. What
separates them, and the shape `fixtures/` needs: one document per rule violating
exactly that rule, one satisfying every rule, then assert the **set of rule
codes** each produces. Two legs that are easy to skip and were both needed here:

- Every entry of a multi-path `given` needs its own hit. A document planting the
  same violation at each covered position proves all of them at once; one that
  only exercises `components.schemas[*]` leaves the other paths unproven.
- Every entry of a `then` array needs its own violating case. The sunset rule's
  `pattern` leg (a malformed `x-sunset`) never runs against a fixture that only
  omits the field.

Also worth a tolerance case per rule, not just a violation: the typeless-schema
rule must **not** fire on an `anyOf`/`enum` schema that legitimately carries no
`type`, and the null rule must not fire on `nullable: false`.

## The house-rule fixtures exist now: `fixtures/<valid|violations>/`, keyed by filename

`packages/contract-tooling/fixtures/` is the shared test data for the house
ruleset, and every later gate task (`lint.ts`, `gates.ts`, the integration test,
`pipeline-simulation`) should consume it rather than inlining its own spec
strings. The contract downstream code depends on:

- `violations/<rule-code>[.<leg>].yaml` must report `<rule-code>` and no other
  code. **The expected code is the filename up to its first `.`**, so a suite
  derives expectations instead of carrying a table that drifts when a rule is
  added. The optional `.<leg>` segment names which `then` entry it exercises.
- `valid/satisfies-all-rules.yaml` must report nothing.
- Six rules, nine violation documents -- rules 4, 5 and 6 each carry a two-entry
  `then`, and each entry needs its own document.

Two closure checks worth re-running whenever a rule is added, both cheap and
both catching a failure that is otherwise silent: no rule in the ruleset lacks a
fixture, and no fixture names a rule that does not exist. A fixture whose name
no longer matches a renamed rule still passes its own assertion.

Assert the **set** of distinct codes, never a finding count: `$ref` resolution
double-reports a violation on a referenced schema (measured: 1 planted breach on
a `$ref`d schema -> 2 findings), so `toHaveLength(1)` is flaky by construction.

## A mutation control that silently tests an EMPTY file instead of a mutation

Bit me while proving these fixtures discriminate, and it is invisible because
the control still reports the failure it was supposed to report -- for entirely
the wrong reason. In Python, `open(p,'w')` is evaluated **before** the argument
expression, so

    open(p,'w').write(open(p).read().replace(a, b))   # WRONG - wipes the file

truncates `p` to zero bytes and then reads the now-empty file. The "mutated"
fixture is an empty file. A linter/parser then fails on it, the control prints
the expected FAIL, and nothing about the run says the mutation never applied.
Same trap in shell: `cmd < f > f` and `sed ... f > f` truncate before reading.

Read first, write second, and assert the edit changed something:

    src = open(p).read()
    out = src.replace(a, b)
    assert out != src, 'mutation did not apply'
    open(q, 'w').write(out)

The `assert out != src` is the load-bearing line -- it is what separates a
control that mutated the file from one whose search string silently missed. Do
the mutation on a copy under /tmp, never in the tracked tree.

## Exit 2 from a gate binary has TWO causes; conflating them hides a dead gate

Refines the vacuum-outcomes note above, and applies just as much to `oasdiff`
and to anything else `gates.ts` composes. Measured on vacuum 0.30.3: exit 2
covers an unparseable document under test, an unreadable document, a missing
ruleset AND a malformed ruleset. The first is a fact about the document; the
rest mean the gate never ran. A wrapper that reports all four the same way
turns "the gate is broken" into "your spec is broken", and the reverse is worse.

The split that works, and the repo convention it matches:

- Pre-check the paths yourself with `existsSync` before spawning. vacuum
  reports missing spec and missing ruleset with the same exit code and
  distinguishes them only by message wording, which breaks on upgrade.
- Discriminate the remaining exit 2 on whether the output names the SPEC path
  (stable) rather than on the wording (fragile). It does for a parse failure;
  it does not for a ruleset failure.
- Then follow `tools/control-byte-gate`: the document being bad is a returned
  finding, the gate being unable to run is a throw. A gate that cannot run must
  never be mistaken for a gate that passed.
- Prefer the binary's **stderr** for the human text: vacuum writes a clean
  `Error: ...` line there and an ANSI-coloured banner to stdout.

A related silent pass with no defence at this layer: a ruleset whose rules are
nonsense (unknown function, `given` that matches nothing) exits 0 with `[]`.
Only per-rule fixtures catch that.

## Three leaf-gate rules that cost a red run each time they are rediscovered

Each bit while writing a leaf module; all three apply to every remaining
`src/*.ts` in this repo.

- `@stylistic/multiline-ternary: 'always'` means EVERY ternary spans three
  lines, including a short one inside an object spread. `--fix` handles it, but
  the failure reads as a formatting opinion rather than a rule.
- `NodeJS.ErrnoException` fails `no-undef`: `eslint.base.mjs` registers node
  globals but no `NodeJS` namespace type. Spell it `Error & { code?: string }`.
- `@stylistic/quotes: 'single'` rejects a template literal carrying no `${}`.
  A wrapped error message concatenated with `+` therefore mixes quote styles on
  purpose: the segment holding the interpolation stays a backtick literal,
  every other segment must be single-quoted.

## A leaf's `*.test.ts` is linted but never type-checked

## You cannot write an ANSI-stripping regex literal in this repo

Corollary of the control-byte gate that any code reading a Go binary's coloured
output runs into. A `/\x1b\[[0-9;]*m/` literal is fine, but the moment the real
byte lands in the file — an agent write path decoding JSON collapses the
four-hex escape — `gate:control-bytes` and `house/no-unsafe-unicode` both
reject it, and `eslint`'s `no-control-regex` objects to the escape form. Build
it from the code point instead, which sidesteps both:

  const ANSI_SGR = new RegExp(`${String.fromCharCode(27)}\\[[0-9;]*m`, 'g');

Skill: `ascii-source-unicode-via-codepoints`.

## `diffSpecs` is gate 3; the same "exit code says nothing" trap as vacuum

`packages/contract-tooling/src/diff.ts` exports
`diffSpecs(basePath, revisionPath, options?)` returning
`{ breaking, changes }`. `gates.ts`, `scripts/pipeline-simulation.ts` and
acceptance script 02 should call it rather than spawning oasdiff themselves.
`breaking` is `changes.length > 0`: `oasdiff breaking` reports breaking
changes and nothing else, and the warning-level ones ("breaking for some
clients", e.g. `request-parameter-removed`) block too.

Measured on oasdiff 1.31.0, each one a wrapper that silently never fails if
ignored:

- `oasdiff breaking` exits **0 whether or not it found breaking changes**
  unless `--fail-on ERR|WARN` is passed. Derive pass/fail from the parsed
  report, which also leaves the exit code free to mean only "could not run".
- `-f json` writes a bare array to stdout with no banner. Fields: `id` (the
  check id), `text`, optional `comment`, `level` (**3 error, 2 warning, 1
  info**), `operation`, `operationId`, `path`, `section`, and `baseSource` /
  `revisionSource` objects of `{file, line, column}` -- both optional, and a
  pure addition or removal only populates one of them.
- `--color` is **rejected outright** under `-f json`: exit **100**,
  `Error: --color flag is only relevant with 'text' or 'singleline' formats`.
  A third exit code beyond 0 and the 102 below.
- A load failure on either side -- missing file or unparseable document --
  exits **102** and writes a plain (no ANSI) `Error: failed to load base spec
  from "<path>"` / `failed to load revision spec from "<path>"` to stderr.
  Same exit for both causes, so pre-check the paths yourself if "which side"
  needs to be reported without parsing oasdiff's wording.
- `oasdiff checks changelog -f json` lists all 681 checks with their levels.
  It is the way to confirm a check id exists before naming a fixture after it.

## Two asymmetries in what oasdiff calls breaking, both easy to get backwards

These are governance facts, not tooling trivia: they decide what
`docs/breaking-changes.md` can claim, what acceptance script 02 has to remove
to be blocked, and which direction a contract change is safe in.

- **Removing an OPTIONAL response property is not breaking.** Only a required
  one is (`response-required-property-removed`). "The diff gate catches
  removals" is false as stated. An acceptance script that removes an optional
  field will exit 0 and prove nothing.
- **Narrowing is breaking in the REQUEST direction only.** Tightening a
  response property from `number` to `integer` reports nothing -- the provider
  promises less variety, which no consumer can be hurt by. The same edit on a
  request property is an error (`request-property-type-changed`), because it
  shrinks what the provider accepts and rejects a consumer already sending
  `1000.50`.

A third one worth knowing before writing `gates.ts`: a document that is valid
YAML but is **not** an OpenAPI description parses without complaint and is
reported as every path removed -- maximally breaking rather than silently
clean. That fails in the safe direction, but nothing in the diff gate can tell
it from a real mass removal. Gate order in spec section 8 (emit, then lint,
then diff) is what covers it.

## `import type` sorts into its own group, and it goes FIRST

`sharedRules.mjs` sets `import/order` groups to
`['type', 'builtin', 'external', 'internal', 'parent', 'sibling', 'index']`
with `newlines-between: 'always'`. So a type-only import sorts **above**
`node:fs`, separated by a blank line, which looks wrong and is what the rule
wants:

    import type { BinaryRun } from './runBinary';

    import { existsSync } from 'node:fs';

    import { runBinary } from './runBinary';

Worth knowing before the first `import type` in a package: it is a lint error
rather than a style opinion, and the fix is counter-intuitive enough to cost a
red run each time it is rediscovered.

## Fixture directories under `packages/contract-tooling/fixtures/` are per gate

`fixtures/valid/` and `fixtures/violations/` belong to the lint gate;
`fixtures/diff/` (a `base.yaml` plus `breaking/` and `not-breaking/`
revisions) belongs to the diff gate. Two conventions are shared across both
and are worth keeping for any gate fixtures that land later:

- **The expected code is the filename up to its first `.`**, so a suite
  derives its expectations instead of carrying a table that drifts.
- **Each directory carries its own README** stating what a file there must do
  when the gate runs. `fixtures/README.md` is the lint one and points at
  `fixtures/diff/README.md`; both are linted, because `eslint.base.mjs`
  declares a `**/*.md` block.

`fixtures/diff/base.yaml` and every revision under it also satisfy the house
ruleset, so the gate-runner integration test can reach the diff gate: a
baseline that failed lint would stop a composed run before diff, and the diff
gate would then read as passing.

## A pair-based fixture suite needs a "the revision actually differs" guard

The diff analogue of the empty-file mutation trap above, and it is silent in
the same way. A `not-breaking/` fixture identical to its baseline reports
nothing, passes its own assertion, and proves nothing about the gate. One
line closes it, asserted for every fixture in both directories:

    expect(readFileSync(fixture, 'utf8')).not.toEqual(readFileSync(base, 'utf8'));

Verified by mutation: copying `base.yaml` over a not-breaking fixture reddens
exactly that case and nothing else.

## `latestPublishedSpec` supplies gate 3's base document; `null` is an answer

`packages/contract-tooling/src/publishedBaseline.ts` exports
`latestPublishedSpec(contractPackageDir)`, returning the ABSOLUTE path of the
highest document under `<pkg>/openapi/published/`, or `null`. `gates.ts`,
`scripts/pipeline-simulation.ts`, acceptance script 01 and the CI publish step
should call it rather than globbing that directory themselves.

Two conventions it fixes, which the emit tasks and the publish step have to
match:

- Baselines are named `<major>.<minor>.<patch>.json` — release versions only.
  A prerelease, a `v` prefix or a two-segment name **throws** rather than
  being skipped, because skipping silently resolves to the second-highest
  version and the diff gate then reports "no breaking changes" against a
  baseline nobody published. Non-`.json` files (a README) are ignored.
- `null` means the package has published nothing yet. An absent
  `openapi/published/` and an empty one give the same answer, and gate 3 has
  to read it as "nothing to compare against" rather than as a failure. A
  `contractPackageDir` that is not a directory throws instead, so a typo'd
  path can never read as "not published yet".

Any case asserting a `null` or a refusal needs a positive control in the same
test — writing one version into that same directory afterwards and asserting
it is now found is what separates "the directory is empty" from "the resolver
looked somewhere else entirely". Same reason the diff fixtures carry the
"revision actually differs" guard.

## `ts.preProcessFile` answers "does this package import X" — do not hand-roll it

`assertNoDbImport` needs to see every way a source file can reach a package,
and the obvious implementations are all silently wrong. TypeScript's own
preprocessor is already in the repo and gets all of it right, in five lines:

    import ts from 'typescript';
    ts.preProcessFile(source, /* readImportFiles */ true,
                      /* detectJavaScriptImports */ true).importedFiles
    // -> [{ fileName, pos, end }]  pos is the offset of the specifier's first
    //    character, quote excluded, so the line is
    //    source.slice(0, pos).split('\n').length

Measured on typescript 5.9.3. It **does** report `import ... from`, `import
type`, a bare side-effect `import 'x'`, `export * from`, a dynamic `import()`,
and an import wrapped across lines. It **does not** report an import inside a
`//` or `/* */` comment, nor one quoted inside a string literal — both of which
contain every character a search would look for and neither of which is a
dependency. `detectJavaScriptImports` is the flag that adds `require()`; with
it `false`, a CommonJS require of the package is invisible.

`typescript` is therefore a **runtime `dependencies` entry** of
`@marcos-corp/contract-tooling` (pinned `^5.9.3`, same range as the root
devDependency), not a devDependency: `dependencyCheck.ts` is part of the
package's exported surface. It is already in `bun.lock`, so CI needs no extra
step for it — unlike vacuum and oasdiff, this gate has no external binary.

## `assertNoDbImport` is gate 4, and `null`-style "clean" is a returned `[]`

`packages/contract-tooling/src/dependencyCheck.ts` exports
`assertNoDbImport(contractPackageDir)` returning `DependencyFinding[]`, plus
`DB_PACKAGE_NAME`. `gates.ts`, `scripts/pipeline-simulation.ts`, acceptance
script 03 and the `contracts-service-*` "declares no dependency on the db"
tests should all call it rather than scanning the tree themselves.

- `DependencyFinding` is a **discriminated union** on `kind`:
  `manifest-dependency` carries `field`, `source-import` carries `line`. Both
  carry `kind`, `file`, `specifier` and `message`, so a caller that only
  prints findings needs no narrowing; one that reads `field` or `line` does.
- It scans the manifest's four versioned dependency fields plus both
  `bundle`/`bundledDependencies` spellings, and every `.ts/.tsx/.mts/.cts/
  .js/.jsx/.mjs/.cjs` file in the package outside `node_modules`, `dist`,
  `build`, `coverage`, `.tmp` and `.git`. Skipping `node_modules` is
  load-bearing: the isolated linker symlinks a leaf's dependencies there.
- Same split as `lintSpec`/`diffSpecs`/`latestPublishedSpec`: the package
  being bad is a returned finding, the gate being unable to run is a throw
  (directory missing, no `package.json`, manifest not JSON). Every "cannot
  run" message starts `dependency gate cannot run:` — assert that wording, not
  just the offending path, or the case also passes against a check that merely
  lets an ENOENT escape.
- **Type-only imports count.** `import type { Card } from '@marcos-corp/db'`
  emits no JavaScript and costs nothing to install, and is exactly the shape
  spec 2.1 forbids — the published contract type then *is* the row type.

## For a scan gate, the mutation that proves it is the NAIVE implementation

Extends the fixture/mutation notes above with the shape that applies to any
"detects X in source" gate. An arbitrary code mutation proves the suite is
wired up; it does not prove the gate is worth having. What does is mutating
the implementation into the version a reasonable person would have written:

  a text search for the package name   -> must redden the comment and the
                                          string-literal tolerance cases
  a per-line `import ... from` regex   -> must redden the multi-line-import
                                          case (and the tolerance cases)

Both were run here and both reddened exactly those cases. The first round of
this grid also produced the trap worth recording: a mutation *intended* to
model a grep matched quoted strings instead of the package name, so it happened
to get the tolerance cases right and stayed **green** — reading as "the
tolerance cases are vacuous" when the mutation was simply not naive. Write the
mutation to be the implementation you are arguing against, then confirm it
reddens the specific cases that argument predicts, by name.

## `@stylistic/quotes: 'single'` allows a MULTI-LINE template literal

Corrects the note above, which says the rule "rejects a template literal
carrying no `${}`". That is true only for a **single-line** one. eslint's
`quotes` rule exempts any template literal that is tagged, has a substitution,
**or contains a line break**, so a multi-line fixture string in a test needs
neither an interpolation nor an escape:

    const FIXTURE = `                      // fine: multi-line, no ${}
    import { Type } from '@sinclair/typebox';
    `;
    'src/x.ts': `import '${DB_PACKAGE_NAME}';\n`   // fine: single-line, has ${}
    'src/y.ts': "import 'a';\n"                    // ERROR: double quotes

The practical consequence for any suite whose fixtures are source code: write
multi-line fixtures as bare backtick literals, and give single-line ones an
interpolation rather than escaping the quotes inside them.

## One more shell trap: `rm -rf` under /tmp is refused by the permission layer

Adds to the shell-traps section above. A scratch-directory setup that starts
`rm -rf /tmp/<fixed-name>` is denied outright and the whole compound command
never runs. Use `mktemp -d` for a fresh path instead of clearing a fixed one —
it needs no delete, and it also stops two runs from colliding.

## `assertExactContractPins` is the pin gate, and it is DEFAULT-DENY

`packages/contract-tooling/src/pinCheck.ts` exports
`assertExactContractPins(packageDir)` returning `PinFinding[]`, plus
`CONTRACT_PACKAGE_PREFIX` (`@marcos-corp/contracts-`). The CI `pins` job,
`scripts/pipeline-simulation.ts` and acceptance script 05 should call it rather
than grepping manifests themselves. Unlike gates 2 and 3 it needs no binary, and
unlike gate 4 it reads a **consumer's** manifest, not a contract package --
so it runs across `apps/*` and `services/*`, not `packages/contracts-*`.

- **Exactly a semver version passes; everything else is a finding.** Written the
  obvious way -- reject a leading `^` or `~` -- the gate waves through `*`, `x`,
  `0.1`, `0.1.x`, `''`, `latest`, `>=0.1.0`, `file:`, `npm:` aliases and
  `workspace:*`, each of which floats the consumer exactly as far. Measured:
  that naive classifier reddens 17 of the 39 cases here.
- `PinFinding.reason` is a four-member union -- `range`, `wildcard`,
  `workspace-protocol`, `not-a-version` -- so a report can say what to write
  instead, not only that the pin is wrong. All four dependency fields are
  scanned; findings sort by field then package name.
- Same split as the other gates: a bad manifest is a returned finding, a gate
  that cannot run is a throw prefixed `pin gate cannot run:`. Assert that
  wording, not just the path -- a bare `ENOENT` from `readFileSync` names
  `package.json` too and passes a path-only assertion (measured: dropping the
  try/catch reddens exactly one case, and only because of the wording check).
- The near-miss worth keeping in any fixture set:
  `@marcos-corp/contract-tooling` is singular `contract-`, one character short
  of the governed prefix, and is ranged like any other library. A prefix check
  written `@marcos-corp/contract` reports it.

## A bare exact pin already resolves to the workspace package, no `workspace:*`

Load-bearing for every consumer manifest still to be written
(`services/service-b`, `apps/web-a`, `apps/web-b`) and for
`docs/governance.md`. Measured in a throwaway bun workspace with a negative
control, because "but does the pin still install" is the objection the
exact-pin rule always draws:

  "@probe/contracts-x": "0.1.0"   -> symlinked to ../../packages/contracts-x
  "@probe/contracts-x": "9.9.9"   -> bun install EXITS 1, 404 from npmjs.org

So `workspace:*` buys nothing here: bun links the workspace package whenever the
declared version matches it. That makes the exact pin cheaper than the protocol
*and* self-enforcing -- a consumer pinned to a version the workspace no longer
holds fails `bun install` outright, before any gate runs. Spec section 2.2 is
therefore enforced twice over, and the gate's job is catching the ranged
specifier that would have installed fine.

returning an `OpenAPIObject`, plus `OPENAPI_VERSION`, `EmitMeta`,
`COMPONENT_REF_PREFIX`, `UnrepresentableSchemaError` and
`UnrepresentableReason`. The half that decides whether one schema is
publishable is `src/schemaRepresentation.ts`; the split is only the 800-line
file ceiling, and `emit.ts` re-exports the error type so callers see one gate.
`gates.ts`, both `contracts-*/scripts/emit.ts` and acceptance scripts 01-03
should call it rather than building a document themselves.

3.1.0 is fixed by the module and deliberately not a caller's choice: TypeBox
emits JSON Schema 2020-12, which only 3.1 embeds unmodified. 3.0 would need
the lossy rewrite (`nullable`, boolean `exclusiveMinimum`, no `const`) that
spec section 5 picked TypeBox to avoid. Verified downstream rather than
assumed, because a version the rest of the chain mishandles would surface two
gates later: vacuum 0.30.3 lints a 3.1 document against the house ruleset, and
oasdiff 1.31.0 reports `response-required-property-removed` across a 3.1 pair.

Conventions the contract-authoring tasks have to match, because the emitter
imposes rather than infers them:

- **`operationId` is derived from the router keys**, camel-joined for a nested
  router (`{ cards: { activate } }` -> `cardsActivate`). Not read from the
  route. This makes house rule 5's "operationId present" structural instead of
  a convention, and it is the id `api_usage` keys on under spec 2.3.
- **A schema carrying `$id` is hoisted** into `components.schemas` under that
  id and replaced in place by a `$ref`. That is the only way house rule 5 is
  satisfiable at all: it runs `resolved: false` and wants the literal
  `{"$ref": "#/components/schemas/Error"}`, so the shared error schema **must**
  carry `$id: 'Error'` or the emitted document fails gate 2.
- **Only `x-` prefixed keys of a route's `metadata` reach the operation.**
  ts-rest has a `deprecated` flag and nowhere to put the sunset date house rule
  4 demands beside it, so a deprecated operation carries
  `metadata: { 'x-sunset': 'YYYY-MM-DD' }`. Everything else in `metadata` stays
  internal.
- `pathParams` / `query` / `headers` are exploded into parameters, so the
  container object never appears in the document and its
  `additionalProperties` is a service-side concern. `c.router()` puts
  `headers: {}` on every route; that is read as "no parameters", not as an
  unconstrained schema.
- A response with no body is `c.noBody()`. A bare `null` is refused.

Same split as the other gates, with one difference: spec section 8 says emit
*fails*, so both halves throw. `UnrepresentableSchemaError` (carrying `path`
and `reason`) means the contract is unpublishable; a plain `Error` prefixed
`emit gate cannot run:` means the contract or the meta is malformed. Assert the
prefix, not just the path — `gates.ts` discriminates on exactly that.

## Do not reach for `@ts-rest/open-api`; it silently drops every TypeBox schema

Measured on `@ts-rest/open-api@3.52.1`, and it is the exact failure spec 2.4
forbids. It reads a schema only through `isZodType`, so handed a TypeBox route
it emits `responses: { '200': { description: '200' } }` — no `content`, no
schema — and exits 0. The path parameter survives only because ts-rest
synthesises `{type: 'string'}` for those regardless. It also takes a
**non-optional** `zod` peer and depends on `@anatine/zod-openapi`.

Anything reaching for an ecosystem tool here should run the same two-minute
probe first: hand it one TypeBox route and read whether the response schema
survives. A tool that drops it still produces a document, still lints, and
still diffs clean against the last published version.

## `c.type<T>()` is compile-time only — at runtime it is a bare symbol

The single most likely contract-authoring mistake, because ts-rest's own docs
recommend it for non-Zod schemas and it type-checks perfectly.
`c.type<Dashboard>()` returns `ContractPlainTypeRuntimeSymbol`, i.e.
`Symbol(ContractPlainType)`, with no schema behind it. Used in a contract, the
emitted document would state nothing for that payload.

Pass the TypeBox schema object itself. Gate 1 refuses the symbol with reason
`compile-time-type`, so the mistake is caught, but knowing it up front saves a
red CI run per contract.

Two neighbouring runtime facts, both needed to read a ts-rest contract:
`ContractNoBody` and `ContractPlainTypeRuntimeSymbol` are **not** registry
symbols (`Symbol.keyFor` returns undefined), so they can only be compared by
identity through an import — unlike TypeBox's `Kind` and `TransformKind`, which
are `Symbol.for(...)` and therefore match across TypeBox copies. And ts-rest's
`isAppRoute` is `'method' in obj`, which **throws a TypeError** on a string or
number rather than returning false: check the shape yourself first.

## TypeBox spells its JavaScript-only types as JSON-Schema-invalid `type` values

Measured on `@sinclair/typebox@0.34.52`, and the reason gate 1 can decide
representability structurally rather than from a deny-list of constructors:

  Type.Date()       {"type":"Date"}          Type.Undefined()  {"type":"undefined"}
  Type.Void()       {"type":"void"}          Type.BigInt()     {"type":"bigint"}
  Type.Symbol()     {"type":"symbol"}        Type.Uint8Array() {"type":"Uint8Array"}
  Type.Function()   {"type":"Function"}      Type.Constructor(){"type":"Constructor"}
  Type.Promise()    {"type":"Promise"}
  Type.Any()        {}                       Type.Unknown()    {}
  Type.Never()      {"not":{}}

So "type is not one of JSON Schema's seven" catches nine of them and stays
correct when TypeBox adds a tenth. `Any`/`Unknown` need the separate "no
constraining keyword" check — they are the `unrepresentable: "any"` failure
verbatim. `Type.Transform` needs a third check and is the one the other two
cannot see: it emits an ordinary `{"type":"string"}` and is marked only by the
`Symbol.for('TypeBox.Transform')` own symbol.

`Type.Never()` is the awkward one: `{"not":{}}` is valid JSON Schema, but the
`{}` inside it is not publishable, so gate 1 refuses it at path `....not` with
reason `unconstrained`. Worth knowing before reading that message.

## A schema walk must be keyword-driven, never a generic deep walk

Applies to anything traversing JSON Schema in this repo. `const`, `default` and
`examples` hold **values**, not schemas, and a value is free to look exactly
like one — `{"const": {"type": "Date"}}` is an example object, not a Date
schema. A generic "recurse into every object" walk reports it as an
unrepresentable schema, at a path that names a field the author never wrote a
schema for.

Recurse only through the keywords whose value is a schema: single
(`items`, `not`, `if`/`then`/`else`, `contains`, `propertyNames`,
`additionalProperties`, `unevaluated*`, `additionalItems`), array (`allOf`,
`anyOf`, `oneOf`, `prefixItems`) and map (`properties`, `patternProperties`,
`$defs`, `definitions`, `dependentSchemas`). The mutation that proves the
distinction is worth keeping: swap in the generic walk and confirm the
const/default/examples case reddens and nothing else does.

## `--reporter=basic` does not exist in vitest 4, and the failure reads as a test failure

Cost a wrong mutation-control reading. `bunx vitest run x.test.ts
--reporter=basic` exits **1** with a *Startup Error* (`Failed to load custom
Reporter from basic`) and runs no tests at all. In a control that reads only
the exit code, that is indistinguishable from "the mutation reddened the
suite" — the mutation is then recorded as proven when nothing ran.

Two habits that close it, both cheap:

- Always read the `Tests  N failed | M passed (T)` line, never the exit code
  alone, and check `T` matches the expected case count.
- In a shell function driving mutations, remember a failed `python3` heredoc
  does **not** stop the function: the next line runs the suite against
  *unmutated* code and reports a clean pass that reads as "this check is not
  load-bearing". Make the mutation script `assert out != src` and read that the
  assert did not fire before believing the run.

## Proving a gate's checks are load-bearing: mutate each check, predict by name

The grid shape that worked for gate 1 and transfers to any multi-check gate.
Build the case table as a **cross product of position and construct** — every
slot a value can occupy times every construct the gate refuses — then:

- give every slot a **positive control** using the same builder and a valid
  value, or a case passes just as well when the builder is broken for an
  unrelated reason;
- disable one check at a time and confirm the red set is exactly the cases that
  check is responsible for, **by name**. Eight slots x one construct reddening
  together is the signal that the check covers every position; a construct that
  reddens in a response but not in a header is a hole.

Run here for seven checks; each reddened exactly its predicted 8 cases (or 1,
for the walk and the type-array legs). The cross product also found the gap it
was meant to find: with no `type: [...]` case in the table, a check written
only for the string form of `type` passed everything.

## A test that asserts an emitted artifact is *usable* has to run the next gate

Structural assertions on an emitted document — right keys, right shapes — all
pass against a document the next gate rejects. The one that does not is running
the real house ruleset over the emitted document through `lintSpec`, which is
why `src/emit.test.ts` shells out to vacuum for a single case.

Proven non-vacuous by mutation, and this is the pairing worth copying: making
the emitter inline `$id` schemas instead of hoisting them reddens both the
`$ref` assertion **and** the house-rule case, because house rule 5 reads the
unresolved document and wants a literal `$ref`. Making it drop
`additionalProperties` reddens the house-rule case too. Without that case an
emitter that fails gate 2 passes its own suite.

Note this adds a second vacuum consumer to `test:all` beyond `lint.test.ts`.
One case depends on the binary rather than a whole `beforeAll`, so an
unprovisioned machine gets exactly one failure carrying `lint gate cannot run:
could not execute 'vacuum'` plus the `$VACUUM_BIN` escape hatch, and the other
127 cases still run.

## `openapi3-ts/oas31` supplies the document types, and its SchemaObject is narrow

`openapi3-ts@4.6.1` is a runtime `dependencies` entry of
`@marcos-corp/contract-tooling` because `OpenAPIObject` appears in
`emitOpenApi`'s exported signature; only its types are used, so its own `yaml`
dependency never loads. Import from the `oas31` subpath, not the root.

One thing to expect: `SchemaObject` enumerates OpenAPI 3.0's keyword set plus a
few, and its index signature only admits `` `x-${string}` ``. JSON Schema
2020-12 keywords it does not list — `$defs`, `if`/`then`/`else`,
`patternProperties`, `unevaluated*`, `dependentRequired` — are legal in a 3.1
document and are a type error to write into a `SchemaObject` literal. Build the
node as `Record<string, unknown>` and cast once, at the one boundary where the
document is right and the interface is narrow.

## `runGates` composes the four gates; call it rather than sequencing them again

`packages/contract-tooling/src/gates.ts` exports `runGates(options)` returning
a `GateReport`, plus `GATE_ORDER`, `DEFAULT_GATE_RUNNERS` and the
`GateName`/`GateStatus`/`GateOutcome`/`GateRunners` types.
`scripts/pipeline-simulation.ts`, the CI contracts job and acceptance scripts
01-03 should go through it: spec section 8's order is a governance decision,
not a convenience, and a second hand-sequenced copy of it drifts silently.

- **Two entry points.** `{ contract, meta }` runs all four gates;
  `{ specPath }` runs gates 2-4 against a document that already exists and
  reports gate 1 as `skipped`. Exactly one of the two, enforced at runtime as
  well as in the type — both or neither throws `gate runner cannot run:`.
  `contractPackageDir` is required either way, because gate 3 resolves its
  baseline from it and gate 4 scans it.
- **Gates 2 and 3 read a scratch copy of what gate 1 just built**, written
  under `tmpdir()` and removed in a `finally`, never
  `openapi/openapi.json`. Linting the committed artifact would report on the
  last emit rather than on the change under review. The committed artifact is
  kept honest separately, by each contract package's byte-identity test.
- **`report.outcomes` is always all four gates in `GATE_ORDER`.** Gates after
  a failure carry status `not-run`; `report.failure` is the failed outcome,
  carrying a `summary` and a `reasons` list built from that gate's findings.
- **Four statuses, and three of them are not `passed`.** `skipped` means the
  gate had nothing to do (no contract supplied, or no baseline published yet)
  and says nothing about the contract — it must not short-circuit anything
  and must not make `ok` false. `not-run` means an earlier gate failed.
- **Same failure/cannot-run split as every other gate here**, and it is what
  makes `ok: false` mean "the contract is bad" rather than "the CI machine is
  missing a binary". Gate 1's two throws are discriminated on
  `instanceof UnrepresentableSchemaError` — that one becomes a failed gate,
  every other error propagates untouched.

## Ordering and short-circuiting are invisible in a returned report

Applies to `scripts/pipeline-simulation.ts` and to anything else that
composes steps. An implementation that runs every step and then labels the
later ones `not-run` returns a byte-identical report to one that stops — while
still spawning both Go binaries and scanning a package tree. Asserting the
statuses proves neither claim; the report agrees with itself whatever ran.

What does prove it is a recorded seam: an injectable set of step functions
that logs `(name, args)` per call, then assertions against the call log —
`toEqual([...])` for the order, `not.toContain(name)` for the steps that must
never have run. Two things that seam then needs, or it quietly becomes the
thing under test:

- **Assert the defaults are the real functions, by identity.** A seam nobody
  checks is how the production path stops calling a real gate while every case
  stays green. `expect(DEFAULT_GATE_RUNNERS.lint).toBe(lintSpec)` is the whole
  check.
- **Never build the recorder by spreading the real defaults.** A recorder that
  falls through for anything it was not told about spawns a binary or reads
  the filesystem, and the case that forgot an override fails for a reason
  unrelated to the composition.

Proven by four mutations, each predicted by case name before running and each
reddening exactly those: dropping the early return after a failed gate (2
red), moving the cheapest gate first — the plausible naive implementation (8
red), dropping the `instanceof` discrimination on gate 1's two throws (1 red),
and reporting a `skipped` gate as `passed` (1 red). Related global skills:
`mutation-leg-grids`, `prove-reuse-with-a-counting-accessor`.

## A published baseline is JSON; the fixtures are YAML. Convert, never copy

`latestPublishedSpec` recognises `<major>.<minor>.<patch>.json` and ignores
everything else, so a scratch `openapi/published/` seeded with a `.yaml`
fixture resolves to `null` and gate 3 reports `skipped` — a passing report
about a gate that never ran. Copying the fixture under a `.json` name works
(oasdiff will diff a JSON base against a YAML revision — measured, mixed pairs
are fine) but publishes a file that is not what it claims to be.

`yaml@^2.9.0` is therefore a devDependency of `@marcos-corp/contract-tooling`,
used only by `src/gates.integration.test.ts` to convert a fixture into the JSON
document a contract package would actually commit. It resolves to the copy
openapi3-ts already pulled in, so it adds nothing to the tree. Anything else
seeding a published baseline — `scripts/pipeline-simulation.ts`, the acceptance
scripts, the CI publish step — should do the same.

## The scratch contract package every gate consumer needs, in one place

`src/gates.integration.test.ts` builds one and it is the minimum the four gates
can be pointed at: a `package.json` for gate 4 to read, one `src/*.ts` for it
to scan (an empty tree passes gate 4 for a reason that has nothing to do with
the gate), and optionally `openapi/published/<version>.json` for gate 3. Reuse
that shape rather than rediscovering it, and build it under `mkdtemp` — never
in the tracked tree.

## Make `not-run` a claim by sharing one package across two cases

`not-run` is a statement about ordering, and a report says it whether or not it
is true — the gate after a failure was going to pass anyway, usually. The pair
that fixes it: run the failing-earlier-gate case against a package that *also*
breaks the later gate, and run a second case against **that same package** with
only the document changed, showing the later gate does fail when reached. Then
`not-run` means "there was something to find and nobody looked". Cost: one
shared fixture and one extra case.

Generalises the recorder-seam note above from `gates.test.ts`: the seam proves
ordering with stubs, this proves it with the real gates and no seam at all.

## Measure an integration suite's coverage boundary; do not assume it

Mutating each gate in `gates.ts` and predicting the red set by name (7 legs,
each matching) produced one result worth keeping: disabling the **lint** gate
entirely reddened **zero** cases. Every fixture the integration suite runs is
house-clean, so an end-to-end suite over valid input cannot pin a gate that
only fires on invalid input — `lint.test.ts` owns that claim and the docblock
says so. Run the "disable this gate" mutation for every gate a composed suite
touches; the ones that redden nothing are the boundary, and writing it down
stops the next reader from over-reading the suite.

## `*.test-d.ts` under `src/` IS type-checked; `*.test.ts` is not. Use that

Closes the "a leaf's `*.test.ts` is linted but never type-checked" note above
with a fix that needs no config. Every leaf tsconfig excludes `**/*.test.ts`
and that glob does **not** match `*.test-d.ts`, so a type-level suite named
`<module>.test-d.ts` beside its module is read by `bun run check-types` today.
Measured in `packages/db`, with a negative control:

  bunx tsc --noEmit --listFiles   names *.test-d.ts, omits *.test.ts
  a wrong expectation             exit 2, `TS2344 ... Expected: <x>, Actual:`

`expectTypeOf` imported from `vitest` works there even though vitest never
executes the file — it is a pure type-level helper, and the mismatch surfaces
as an ordinary tsc error. So the split for any leaf is: `*.test.ts` is gated by
`bun run test`, `*.test-d.ts` by `bun run check-types`. Say which in the file's
docblock, or the next reader assumes the runner covers both.

**Do not reach for vitest's `typecheck` mode instead.** With
`typecheck.enabled: true` it reads the leaf tsconfig, inherits the
`**/*.test.ts` exclude, type-checks **zero** files and prints
`Type Errors  no errors` — measured: a blatant `const x: string = 1;` in the
included file stayed green, and so did an inverted `toEqualTypeOf`. It only
reddens once pointed at a tsconfig that includes the test files, at which point
it has bought nothing over the `.test-d.ts` route and added an experimental
flag plus a second tsconfig.

## Runtime and type assertions over the same module are not redundant

General to any schema, config or builder module whose source states two
separate things. Proven by mutation in `packages/db`, predicting the red set by
case name before each run; six legs, all matching:

  rename a SQL column                 check-types GREEN, test RED (2 cases)
  drop a FK's `onDelete`              check-types GREEN, test RED (1 case)
  add a SQL DEFAULT                   check-types RED (1), test RED (3)
  add a member to a DB enum           check-types RED (3), test RED (2)
  relax a column to NOT NULL          check-types RED (2), test RED (2)
  naive helper: SQL name == property  check-types GREEN, test RED (3)

The first two are the boundary worth writing down: an inferred type erases
every SQL name, so `check-types` cannot see a rename at all. The type suite
owns the TypeScript property names and their types; the runtime suite owns the
SQL names, types, nullability, defaults and keys. Neither can make the other's
claim, and a suite that only does one of them reads as covering both.

## Reading a Drizzle table back as data, and where the helper lives

`packages/db/src/testing/tableFacts.ts` exports `columnFacts`, `sqlTableName`,
`foreignKeyFacts`, `primaryKeyFacts` and `indexFacts`. Every remaining schema
task in `packages/db` should import it rather than re-deriving the
introspection, and any suite asserting what a migration will emit should go
through it.

- `getTableColumns` / `getTableName` come from `drizzle-orm`;
  `getTableConfig` (foreign keys, indexes, unique constraints) is
  `drizzle-orm/pg-core` and takes a `PgTable`.
- **`column.getSQLType()` is the assertion worth making** — it renders exactly
  what `CREATE TABLE` writes, length, enum type name and `with time zone`
  included (`varchar(11)`, `char(3)`, `timestamp with time zone`). Stronger and
  far more readable than `columnType` (`PgVarchar`), which says nothing about
  length.
- A column's `.unique()` shows up as `column.isUnique`, **not** in
  `getTableConfig(table).uniqueConstraints` — that list stays empty. Reading
  only the constraint list reports every column as non-unique.
- `foreignKey.reference()` is a thunk (tables may point at ones declared later
  in the module graph); calling it is what resolves the referenced table.
- Assert the **whole** `columnFacts` record with one `toEqual`. A per-column
  check passes just as happily when a column is added or dropped, which is the
  change most likely to arrive without anyone reopening the suite.

## drizzle-orm 0.45.2: every peer is optional and `pg-core` means it

Unlike `@ts-rest/core`'s optional-zod peer, which is a lie at runtime (see
above), drizzle's is real. All 29 peers are `optional: true` and they are all
drivers; `drizzle-orm/pg-core` builds tables, enums and constraints with no
driver installed at all — verified by importing it and rendering a table with
nothing but `drizzle-orm` in the tree. So a package that only declares schema
needs exactly one dependency, and the driver arrives with the task that opens
a connection.

## `newline-per-chained-call` breaks every Drizzle column builder

Adds to the three leaf-gate rules above. `ignoreChainWithDepth: 2` means
`uuid('id').primaryKey().defaultRandom()` and `.notNull().unique()` are lint
errors. `eslint --fix` handles it and the result is the repo's house style, so
run `bunx eslint . --fix` before reading the failures as a design problem —
but expect every schema module to come out with its chains split across lines.

## A composite primary key hides from `columnFacts` — read `primaryKeyFacts`

`.primaryKey()` on a **column** builder sets `column.primary`; a table-level
`primaryKey({ columns: [...] })` does not touch any column. So every column of
a composite key reports `isPrimaryKey: false`, and a suite asserting only
`columnFacts` describes the table as having no key at all — green, and wrong.
`primaryKeyFacts(table)` reads `getTableConfig(table).primaryKeys` and returns
`{ name, columns }`; drizzle derives the name as
`<table>_<col>_<col>..._pk`, so a rename that pushes it past Postgres's 63-byte
identifier limit shows up there and nowhere else.

`indexFacts(table)` is the same argument for indexes: an index reaches no
inferred type and no `columnFacts` entry, so a refactor that drops one is a
silent seq-scan regression that passes all four gates. Its `name` and `method`
are `string | undefined` in drizzle's types — an anonymous `index()` has its
name derived later by drizzle-kit — so the interface says so rather than
casting.

## Declare drizzle indexes ASCENDING even when every read sorts newest first

Repo decision, taken with `transactions_company_id_booked_at_idx`, and it
applies to every index still to be added here. Drizzle's index column builder
renders `.desc()` as `DESC NULLS LAST` — the opposite of Postgres's default for
a descending sort — and the planner matches a pathkey literally, so such an
index is unusable by a plain `ORDER BY x DESC` **even on a NOT NULL column**.
An ascending index carries no nulls qualifier and is simply read backwards for
the same query.

Consequence for the repository layer: write the ordering as a bare
`ORDER BY <col> DESC`. Do **not** "match the index" by spelling
`desc nulls last` — that is the fix for the opposite mistake (an index already
declared `.desc()`), and here it would cost the index instead of using it.
Skill: `drizzle-order-by-nulls-last-pathkey`.

## Money columns: `integer` minor units, and the two ways that type drifts

- The ceiling is 2 147 483 647 minor units — 21 474 836.47 in a two-decimal
  currency. Widening to `bigint` is a migration the provider owns and a change
  no consumer can see, because the contract states its own integer type
  independently. That is worth saying in the module rather than discovering at
  the overflow.
- **drizzle renders `bigint` and `numeric` as TypeScript `string` by default**,
  so both the widening above and a well-meant "money should be numeric" change
  silently turn every arithmetic site into string concatenation. Pin
  `expectTypeOf<Row['xMinorUnits']>().toEqualTypeOf<number>()` in the leaf's
  `.test-d.ts`; nothing else in the four-gate order catches it.

## Three shapes of contract/database divergence, and only one is a rename

The stage note says column names must be "deliberately unlike the contract
field names". Taken literally that produces a thesaurus exercise. What the
tables actually landed, and what the mapping tasks in `services/service-a`
should expect to translate:

- **A renamed column** — `cards.lifecycle_status` for the contract's card
  state. The weakest of the three: a mapper that only renames is a rename.
- **A structural difference** — `transactions` stores `amount_minor_units` and
  `currency_code` as two flat columns; the contract publishes one money object.
  And `merchant_category_code` is a raw open-set ISO-18245 MCC where the
  contract publishes a coarse enum, which is the concrete reason spec §2.5
  needs an explicit `unknown` member: a new MCC in the acquirer feed must not
  break a pinned consumer.
- **A field with no column at all** — the `5 400` of `5 400/10 000 kr`.
  `spend_limits` stores the cap and nothing else; remaining spend is the cap
  minus the settled transactions in the window. A derived schema could not
  produce the payload the screen renders, which is the strongest single
  argument in this repo for spec §2.1.

Assert the third kind as an absence (`sqlNames` does not contain `remaining`),
or the case that a later "just cache it" column would break does not exist.

## `ON DELETE` is a per-table judgement; assert it or it gets unified

`spend_limits` cascades from `cards` (configuration scoped to a card);
`cards`, `transactions` and everything else restrict (a financial record must
not vanish with its parent). One table differing from the rest reads as an
oversight to the next person, so the divergence is asserted with a case whose
name says why. Inferred types erase `onDelete` entirely — measured again here:
flipping cascade to restrict left `check-types` green and reddened exactly one
named case.

Also worth stating where it bites: two independent foreign keys on a
denormalised child (`transactions.card_id` + `transactions.company_id`) do
**not** enforce that the child's company matches the card's. That needs a
composite key against `cards (id, company_id)`. Record the invariant and its
owner in the module header rather than leaving it to be found in a bad row.

## A drizzle column's `mode` is invisible to `getSQLType()` — only `.test-d.ts` sees it

Sharpens the "runtime and type assertions are not redundant" note above with the
case where the runtime suite is not merely weaker but structurally blind.
`date`, `timestamp`, `bigint`, `numeric` and `json` all take a `mode` option
that decides the **TypeScript** type and changes nothing in SQL. Measured on
`invoices.due_on`: all three of `mode: 'string'`, `mode: 'date'` and the default
render `getSQLType() === 'date'`, so `columnFacts` cannot tell them apart.

Flipping `mode: 'string'` to `'date'` reddened `check-types` with 2 errors, both
in `invoices.test-d.ts`, and left all 40 runtime cases **green**. So for any
mode-bearing column the `.test-d.ts` is not a second opinion — it is the only
gate in the four-gate order that fails, and a table whose type suite omits it
has no coverage of that decision at all. Pin the field's type explicitly per
mode-bearing column, the same way money columns are pinned as `number`.

The repo convention the mode encodes, worth matching in the remaining tables:
an **instant** is `timestamp({ withTimezone: true, mode: 'date' })` reaching
TypeScript as a `Date` (`booked_at`, `activated_at`, `period_started_at`); a
**calendar day** is `date({ mode: 'string' })` reaching it as an ISO
`YYYY-MM-DD` string (`invoices.due_on`), because a `Date` for a calendar day
carries a time-of-day nobody chose and renders as the previous day for a reader
in another zone.

## A "delete the declaration" mutation leg reddens `check-types` for the wrong reason

Mutation-grid trap, general to every leaf here: the leaf tsconfigs set
`noUnusedLocals`, so a leg that removes the only *use* of something orphans its
import and `tsc` reports an unused-import error. Deleting an `index(...)` call
reddened `check-types` with 2 errors — in the schema module, not in any test —
which reads as "the type suite covers indexes" when the type suite never saw it.

Two habits that keep the grid honest, both cheap:

- Read **which file** the tsc errors are in, never just the count or the exit
  code. An error in the module under mutation is usually the mutation's own
  collateral; an error in a `*.test-d.ts` is the claim you were testing.
- Prefer a leg that *changes* a declaration over one that deletes it (rename the
  column, flip the `onDelete`, swap the `mode`). A change keeps every binding
  used, so the only red left is the assertion you predicted.

## A mutation grid over a module cannot redden an *absence* case — invert those

Every leg in a schema mutation grid changes something the module declares, so
it reaches only the cases that assert presence. A case asserting the opposite —
no foreign key, no rollup column, no unique index, no `overdue` member — stays
green under all of them, which reads as "covered" and is not. The grid needs a
second half whose legs **add** the thing each guard forbids:

  add a FK to a parent table   -> the "declares no foreign key" case
  add a `call_count` column    -> the "stores no derived figure" case
  `index()` -> `uniqueIndex()` -> the "makes neither index unique" case
  column key -> `primaryKey({})` -> the "keys on the surrogate column" case

Ten legs over `api_usage` (seven changing, three inverting) reddened all nine of
its cases; the changing seven alone reached six. Cheap, and it is the only thing
separating a guard that holds the line from a sentence in a test file. Global
skill: `accepting-cases-need-inverted-legs`.

## A type-changing mutation must fix the import, or 9 cases VANISH and read as red

Sharpens the `--reporter=basic` note above with the shape it actually takes in
this repo. Swapping `smallint('x')` for `integer('x')` without adding `integer`
to the `drizzle-orm/pg-core` import makes the module fail to load, so vitest
reports:

  Tests  40 passed (40)      exit 1     <- the whole file never ran
  Tests  1 failed | 48 passed (49)      <- what the mutation actually proves

Both are exit 1. The tell is the **total**: 49 dropped to 40, i.e. the nine
cases disappeared rather than failing. A grid driver that reads only the exit
code records the leg as proven when nothing was measured. Always assert the
total case count is unchanged before reading which cases went red — and prefer
legs that keep every binding used, per the `noUnusedLocals` note above.

## `bigserial` joins the mode-bearing columns that `getSQLType()` cannot see

Adds to the `date` / `timestamp` / `bigint` / `numeric` / `json` list above.
`bigserial` renders as `bigserial` under both `mode: 'number'` and
`mode: 'bigint'`, so `columnFacts` cannot tell a `number` id from a `bigint`
one and the colocated `.test-d.ts` is the only gate in the four-gate order that
fails when it changes. Measured: flipping the mode left all 49 runtime cases
green and reddened `check-types` in `apiUsage.test-d.ts` alone.

Also worth knowing before asserting one: a bare `bigserial(...)` reports
`notNull: false` — the serial default does not imply it. Only `.primaryKey()`
or an explicit `.notNull()` sets it.

## `api_usage` inverts the naming rule the rest of the schema follows — do not "fix" it

`packages/db/src/schema/apiUsage.ts` is the telemetry table spec §2.3 requires,
and the four later tasks that read it are `services/service-a`'s
`usageLogger.ts`, acceptance script 04 (§9.4), `docs/field-retirement.md` (§6.4)
and the affected-consumer list a major version needs (§6.2). Two properties it
does not share with its five siblings, both deliberate and both easy to
"correct" into a bug:

- **Its columns are spelled exactly like the contract vocabulary**, not
  deliberately unlike it. The divergence rule exists because a contract derived
  from a table publishes the schema (spec §2.1); this table publishes nothing
  and *describes* a contract, so `client_id`, `operation_id` and
  `contract_version` matching the emitted document's own spelling is the entire
  point — a rename breaks the join and buys nothing. A case asserts the
  agreement, so the "fix" fails rather than lands.
- **It declares no foreign key at all.** A telemetry row must outlive the rows
  it describes: `RESTRICT` would let a log entry block an operational delete and
  `CASCADE` would erase the evidence. Asserted as `toEqual([])` with a comment
  saying why, because an empty list next to five tables that all reference their
  parent otherwise reads as an oversight.

Spec §6.4's 13-month retention is **not** implemented — no partitioning, no
rollup, no expiry job — and a case asserts no rollup column exists so it cannot
be half-implemented here instead. `docs/field-retirement.md` records it as a
documented requirement rather than a shipped one.

## `drizzle-kit generate` EXITS 0 when it crashes on an interactive prompt

The single most dangerous thing about wiring this command into a script, and it
is silent in the worst direction. A column **rename** makes drizzle-kit ask
"renamed, or dropped and added?"; in a non-TTY shell (an agent's Bash tool, CI)
it throws `Error: Interactive prompts require a TTY terminal`, writes no
migration at all, and **exits 0**. Measured on drizzle-kit 0.31.10.

So `bun run db:generate; echo $?` is not a reading. What is:

  `[✓] Your SQL migration file ➜ drizzle/NNNN_<name>.sql`  -> a file was written
  `No schema changes, nothing to migrate 😴`               -> snapshot in sync
  neither line                                             -> nothing happened

The neighbouring exit codes, since they are not consistent with each other: a
`schema` path matching no file exits **1** with a clear
`No schema files found for path config [...]` and emits nothing, and an
additive change (a new column, a new table) never prompts and exits 0 having
written the file. Only rename-shaped diffs prompt. A CI step that generates
must therefore assert the printed line, and a rename is a change a human runs
interactively before committing.

## Two controls that prove a committed drizzle snapshot is honest

`drizzle/meta/*_snapshot.json` is the base every future migration diffs
against, and a snapshot that does not describe the committed schema produces
correct-looking SQL for a database nobody has. Neither gate in the verification
order opens `drizzle/`, so this is hand-run per schema change:

- **Idempotency.** Re-run `bun run db:generate`; it must print `No schema
  changes, nothing to migrate`. A second migration file appearing means the
  first one did not capture the schema.
- **Liveness.** Copy `drizzle/` to `.tmp/drizzle-probe/`, point a throwaway
  config at it, apply an **additive** mutation to a schema module, and confirm
  a `0001_*.sql` carrying the expected `ALTER` appears. Then `git checkout` the
  module and delete `.tmp/`. Without this, "no schema changes" is
  indistinguishable from a config whose `schema` path resolves to something
  else entirely.

Use an additive mutation, never a rename — see the TTY note above, where a
rename control exits 0 having done nothing and reads as a passing check.

## Point drizzle-kit's `schema` at `src/index.ts`, not at `src/schema/*.ts`

The glob also matches the colocated `*.test.ts` and `*.test-d.ts` modules,
which drizzle-kit bundles and executes for their exports. Pointing at the
package's own entrypoint avoids that and buys a second property worth having:
"exported from `src/index.ts`" and "reaches a migration" become the same set,
so a table nobody exports cannot silently miss the DDL.

## drizzle-kit is a LEAF devDependency, and `generate` contacts no database

Same exception as `@types/express` — the "tooling devDeps stay at the root"
note is about *shared* tooling, and under bun's isolated linker the CLI and its
`defineConfig` type must resolve from the package directory. It lands in
`packages/db/node_modules/.bin/drizzle-kit`.

`dbCredentials` is **not read by `generate`** — verified by running under
`env -u DATABASE_URL`, which generated the full migration and exited 0.
Generating is a pure diff between the schema modules and the last snapshot. So
`drizzle.config.ts` carries `process.env.DATABASE_URL ?? ''` with no committed
fallback connection string: a default there is how a migration ends up applied
to whatever database happened to be listening, and it buys nothing for the one
command that runs today.

## Assert the generated DDL, not only the schema module — the SQL is what runs

Four cross-checks worth re-running whenever a table or index is added, each of
which the schema module states but only the SQL settles. All four passed for
the initial migration:

- **No identifier exceeds Postgres's 63-byte limit.** drizzle derives
  constraint and index names by concatenation, so a composite key is the one
  that goes over first (longest here:
  `spend_limits_card_id_reset_period_period_started_at_pk`, 54 bytes) — and it
  is truncated by Postgres rather than refused, which is worse.
- **No `CREATE INDEX` carries `DESC` or `NULLS`.** That is the ascending-index
  decision recorded above, and the emitted SQL is the only place it is visible.
- **The `ON DELETE` split survives** — one `cascade`, four `restrict` here.
- **A table that must own no foreign key still owns none.**

`drizzle/` is outside `eslint` (leaf ignores `drizzle/**`) and outside `tsc`
(leaf tsconfig excludes it), so nothing but `gate:control-bytes` ever opens
those files. That gate accepts tab, newline and CR, so drizzle's tab-indented
`CREATE TABLE` bodies pass unchanged.

## `drizzle.config.ts` at a leaf root IS read by both leaf gates

It matches the leaf tsconfig's `include: ["src", "*.ts"]` and is not in any
ignores block, so `eslint .` and `tsc --noEmit` both cover it — confirmed with
negative controls (a double-quoted string reddened lint; an invalid `dialect`
literal reddened `check-types` with TS2322 naming the six legal dialects). That
last one is worth knowing: drizzle-kit's config types are strict enough that a
typo'd dialect or option is a `check-types` failure rather than a runtime one.

## `pg` is the driver, and its version is NOT in lockstep with `@types/pg`

`packages/db` opens its first connection with `drizzle-orm/node-postgres` plus
`pg`, which is the combination `.claude/skills/drizzle-orm/rules/` documents.
Any later task that connects — `service-a`'s repositories, the integration
suites, `scripts/demo.ts` — should use the same pair rather than reaching for
`postgres`/postgres.js or `bun:sql`, both of which drizzle also supports and
neither of which the repo's own skill covers.

- `pg` is a **runtime `dependencies`** entry of the package that connects;
  `@types/pg` is a **leaf `devDependencies`** entry, the same exception as
  `@types/express` (the "tooling devDeps stay at the root" note is about
  *shared* tooling).
- The two versions are published independently: `pg` latest is **8.23.0** while
  `@types/pg` latest is **8.23.1**, so `bun add pg@^8.23.1` fails with
  `No version matching "^8.23.1" found for specifier "pg" (but package
  exists)`. Read `npm view <pkg> dist-tags` rather than assuming the types
  version is installable for the runtime package.
- drizzle's `pg` peer is `>=8` and optional, and unlike `@ts-rest/core`'s
  optional zod peer it means it: `drizzle-orm/pg-core` still needs no driver.

## `pg` reports a refused connection as an `AggregateError` with an EMPTY message

The idiom this repo already uses in several places —

    const message = err instanceof Error ? err.message : String(err);

— prints **nothing** for the single likeliest failure of any script that
connects to Postgres. `pg` raises an `AggregateError` (one sub-error per
resolved address) whose own `message` is `''`, and `AggregateError` passes
`instanceof Error`, so the operator gets `FAIL — ` and no cause. Measured
against a closed port; the sub-errors carry the `connect ECONNREFUSED
::1:<port>` text.

Any catch that renders an error for a human in a package that talks to a
database needs the recursive form instead:

    if (err instanceof AggregateError && err.errors.length > 0) {
      return err.errors.map(describeError).join('; ');
    }
    if (err instanceof Error) { return err.message || err.name; }

The `|| err.name` half matters on its own — an `Error` with an empty message is
not only an `AggregateError` thing. Bad credentials and a missing table both
report fine through `err.message`, so a probe that only tests those two reads
as proving the handler works.

## The seed's shape, and why it is NOT exported from `packages/db/src/index.ts`

`packages/db/src/seed.ts` exports `seedDatabase(db, options?)`,
`buildSeedRows(options?)` (pure, no database), `SEED_FIGURES` and the fixed
`SEED_COMPANY_ID` / `SEED_CARD_ID` / `SEED_DUE_INVOICE_ID` /
`SEED_PAID_INVOICE_ID`. The integration suite, `service-a`'s mapper tests,
acceptance script 04 and `scripts/demo.ts` should import these rather than
re-deriving the demo's numbers.

- **It is reachable as `@marcos-corp/db/seed`, a second `exports` subpath, and
  deliberately not re-exported from `src/index.ts`.** That file is the `schema`
  entry of `drizzle.config.ts` and drizzle-kit *executes* it for its exports, so
  re-exporting a module that imports a driver would put `pg` on the path of
  `bun run db:generate` — a command that contacts no database by design. Adding
  the subpath left `db:generate` printing `No schema changes, nothing to
  migrate`, which is the control worth re-running after any new `src/*.ts`.
- `seedDatabase` takes a `NodePgDatabase` rather than opening its own
  connection, so a test injects a throwaway handle; only the CLI branch builds a
  `Pool`. The CLI is guarded with
  `fileURLToPath(import.meta.url) === process.argv[1]` (skill:
  `esm-dual-purpose-cli-module`) and wired to `bun run db:seed`.
- Everything happens in one `db.transaction`, and the deletes are scoped to
  `SEED_COMPANY_ID` and ordered child-first — verified against a real cluster: a
  failure on the last insert leaves 0 rows in all five tables, three
  consecutive runs leave exactly one copy, and a second planted company's rows
  survive untouched.

## The seed is deliberately non-uniform, and the mapping tasks will be graded on it

Load-bearing for `services/service-a`'s `dashboardMapper` and for `service-b`'s
due-invoice lookup. A seed where every transaction is settled and inside the
spend window would let a mapper that drops either filter compute the right
answer, so the 57 rows are split 47 settled-in-window / 4 unsettled-in-window /
6 settled-before-window, one of the 47 is a **negative** amount, and the newest
row of all is `authorised` rather than `settled` — it belongs in the three the
screen lists but not in the spend the meter subtracts.

The wrong answers are all distinct from the correct `540000`, which is what
makes a test able to tell them apart:

    correct (state + window filters)   540000
    no settlement-state filter         447700
    no spend-window filter             300000
    Math.abs() on the amounts          510000

Same argument for the invoice banner: a second, already-`paid` invoice is due
**earlier** than the issued one, so a lookup written `ORDER BY due_on LIMIT 1`
without `payment_state = 'issued'` returns the wrong row rather than being
accidentally right. There is still exactly one *due* invoice.

## A module-level consistency guard ABSORBS fixture mutations — aim the grid elsewhere

Extends the mutation-grid notes above with a shape that will recur wherever a
module asserts its own invariants at build time. `buildSeedRows` throws on an
inconsistent fixture, and the colocated suite builds its rows at module scope,
so any mutation to the fixture table makes the whole test file fail to load —
every case *vanishes* rather than going red, which is the "9 cases disappeared"
reading recorded above.

That is not a reason to drop either layer; it means they need separate grids:

- **Mutate the fixture to prove the guard.** Nine legs here (an amount, a row
  count, the window width, the newest-row offset, the before-window spacing, an
  invoice state, and three `SEED_FIGURES` entries) each threw a *distinct*
  message. Read the thrown text, not the exit code — a `grep` for the guard's
  wording matches the source line in the stack trace and reports every leg as
  firing the same guard.
- **Mutate what the guard does not cover to prove the suite.** Currency, card
  lifecycle state, the activation instant, the legal/display name split, the
  invoice due dates and the sub-second truncation are outside the guard, and
  eight legs there reddened exactly their predicted cases by name with the
  total holding at 24.

Order the guard's own assertions so the most fundamental run first: placement
before the sums it feeds, or a row on the wrong side of a window reports as
"expected 460000 settled, built 412300" and sends the reader hunting a typo in
an amount.

## A throwaway Postgres for this repo: homebrew `postgresql@14`, migrations applied verbatim

`/opt/homebrew/opt/postgresql@14/bin` is present on this machine and stands a

Count what landed rather than trusting a silent run; the initial migration

## `startThrowawayPostgres` is where a database-backed suite gets its server

`packages/db/src/testing/throwawayDatabase.ts` exports
`startThrowawayPostgres()`, `MIGRATIONS_DIR` and
`THROWAWAY_POSTGRES_TIMEOUT_MS`. Every later suite that needs a real Postgres —
`services/service-a`'s repository and integration tests, `service-b`'s
due-invoice test, acceptance script 04 — should call it rather than reaching for
docker or a hand-rolled connection.

- **Two routes, `TEST_DATABASE_URL` first.** A supplied server wins so a
  deliberately provisioned one is never quietly ignored; otherwise the module
  runs `initdb` into a scratch dir and starts it **on a unix socket with
  `listen_addresses = ''`**, which is why it cannot collide with a Postgres
  already holding 5432. Both routes then hand back a *freshly created,
  uniquely named* database and drop it in `stop()`. Migrating into the URL's
  own database directly is the mistake the create/drop exists to prevent.
- **`stop()` drops every database the handle created**, so a failed run leaks
  nothing onto a shared server. Verified against a real one: `pg_database`
  held no `qred_%` row afterwards.
- Neither route available is one pointed error plus skipped cases, never a
  green run — same shape as the vacuum/oasdiff suites. `PG_BIN_DIR` is the
  escape hatch, and both halves were proven (roots emptied + no Postgres on
  PATH -> the pointed error; same run with `PG_BIN_DIR` set -> 14 green).
- Startup is ~640 ms with `--no-sync` and `fsync = off`, so a per-file server
  is cheap enough not to bother sharing one.

## Pass `pg` a unix-socket directory as `host`, and watch `sun_path`

`new Pool({ host: '/tmp/qred-pg-abc123', user, database })` connects over the
socket — no port, no password, no TCP. Two things to know before copying it:

- The socket path is capped by `sun_path`: **104 bytes on macOS**, 108 on
  Linux, and exceeding it reports neither the socket nor the limit. macOS's
  `TMPDIR` is a ~48-character private path, so `tmpdir()` + a scratch dir +
  `/.s.PGSQL.5432` lands at 77 — inside the budget, but not by enough to
  assume. `throwawayDatabase.ts` measures it and falls back to `/tmp`.
- `listen_addresses = ''` belongs in `postgresql.conf`, **not** in
  `pg_ctl -o`. `pg_ctl` hands that string to a shell, so the empty quotes have
  to survive a quoting round trip the config file does not have.

## An uncast `SUM()` comes back as a STRING, and a naive assertion hides it

Postgres widens `SUM(integer)` to `bigint`, and `pg` renders `bigint` as a
JavaScript **string** because it can exceed the safe integer range. So a
remaining-spend query returns `"540000"`, and `expect(x).toBe(540_000)` fails
for a reason that reads as a wrong figure rather than a wrong type. Cast the
aggregate — `(... - COALESCE(SUM(...), 0))::int` — and then do **not** coerce
on the JavaScript side: a strict comparison against a numeric literal is itself
the check that the money columns are still `integer` and not the `bigint` or
`numeric` the money-column note above warns about. `count(*)` has the same
shape and the same `::int` fix.

## drizzle's `migrate()` beats `psql -f` for a suite, and proves more

`migrate(db, { migrationsFolder })` from `drizzle-orm/node-postgres/migrator`
needs no `psql` on PATH, reads `drizzle/meta/_journal.json` so a second
migration is picked up with no edit, and records what it applied in
`drizzle.__drizzle_migrations` — a separate schema, so `information_schema`
filtered to `public` still lists exactly the six tables. The `psql -f` route in
`throwaway-postgres-probe-cluster` stays the right tool for a *probe*; a
committed suite should migrate the way a service does.

Resolve the folder from `import.meta.url`, never `process.cwd()` — same reason
`HOUSE_RULESET_PATH` does in contract-tooling.

The strongest single leg in the grid over `seed.integration.test.ts`: renaming

## `Type.Union([Type.Literal(...)])` emits no `enum` keyword, so house rule 3 never sees it

The single most consequential thing to know before authoring the remaining
contract enums (card state, settlement state, merchant category, invoice
payment state). Measured on `@sinclair/typebox@0.34.52`:

  Type.Union([Type.Literal('a'), Type.Literal('unknown')])
      -> {"anyOf":[{"const":"a","type":"string"}, ...]}     no `enum` key
  Type.Enum(SomeTsEnum)                                     same, `anyOf`
  Type.Unsafe<'a'|'unknown'>({ type: 'string', enum: [...] })
      -> {"type":"string","enum":["a","unknown"]}           a real enum

House rule 3's `given` is `$..[?(@.enum)]`, so the two idiomatic TypeBox
spellings produce an enum a human reads as an enum, a consumer switches on as
an enum, and the `unknown`-member rule never fires against. The rule stays
green and spec §2.5 stops being enforced on that schema.

`Type.Unsafe<T>` is therefore the repo idiom for a contract enum: it emits the
`enum` array and keeps the TypeScript union. Pair it with a `const CODES = [...]
as const` and derive both the type (`(typeof CODES)[number]`) and the array, so
the union and the published list cannot drift. Verified end to end: emitted
through `emitOpenApi`, vacuum reports nothing; drop the `unknown` member from
the same document and it reports `house-enum-has-unknown-member`.

## `Omit<Options, K>` over a TypeBox option type is a guard that states nothing

`SchemaOptions` carries `[prop: string]: any`, and `ObjectOptions`,
`StringOptions` and the rest all extend it. So
`Omit<ObjectOptions, 'additionalProperties'>` drops every *named* member,
keeps the index signature, and admits `additionalProperties` — plus anything
else — straight back. It compiles, it reads as a restriction, and it restricts
nothing.

Spell the allowed options as an explicit `interface` with no index signature
instead; excess-property checking on an object literal is then a real
`check-types` failure. And prove it with an `@ts-expect-error` line plus its
control: swap the forbidden key for a legal one and confirm tsc reports
**TS2578 Unused '@ts-expect-error' directive**. Without that control a guard
that never bites is indistinguishable from one that does.

## Two things `packages/contracts-service-a/src/schemas/shared.ts` now owns

Later schema tasks in either contract package should import these rather than
restate them:

- **`responseObject` / `requestObject`.** Spec §2.5's asymmetry is encoded in
  the builder, not at the call site: responses get `additionalProperties: true`
  (a consumer must tolerate a field its pinned version predates), requests get
  `false`. Every object in a contract goes through one of them, which is what
  makes house rule 2 satisfied by construction.
- **The `$id` convention.** `emitOpenApi` hoists on `$id`, so objects reused
  across operations carry one and scalars do not — a component per string type
  pushes the constraint one indirection away from the field it constrains. A
  query or path-parameter container must **not** carry one either: those are
  exploded into `parameters`, so the component would be referenced by nothing.

`MonetaryAmount`, `Timestamp`, `PageInfo`, `paginatedResponse`,
`PaginationQuery` and `ErrorResponse` are the primitives; the error schema's
`$id` is the literal `Error` house rule 5 hard-codes.

## Assert a schema through `JSON.parse(JSON.stringify(schema))`, not the object

TypeBox attaches `Kind` and friends as enumerable symbol properties, which
vitest's `toEqual` compares and no gate in this repo ever reads. The JSON round
trip is exactly the reduction `emitOpenApi` writes into the document, so it is
both the honest assertion and the one that does not fight the library.

Two TypeBox emission facts worth knowing before writing the expectation:
`Type.Object({})` emits **no** `required` key at all (not `[]`), and an object
whose properties are all `Type.Optional` does the same. An absent key and an
empty list are different documents; assert whichever one is true.

One trap when a nested expectation reuses a sibling's emitted JSON
(`{ currency: emitted(CurrencyCode) }`): that portion then agrees with itself
under any mutation to `CurrencyCode`, so the claim has to be owned by that
schema's own case. Fine as long as the case exists — the mutation grid is what
shows which one reddened. Skill: `convert-exactly-one-spelling`.

## Two lint/type traps that cost a red run each in a heavily-documented module

- **A JSDoc containing a glob that ends in `*/` terminates the comment.**
  Writing the tsconfig exclude glob for test files inside a docblock is a
  *parsing error* from eslint pointing at the line after it, which reads as a
  syntax problem in the code rather than in the prose. Rephrase, or break the
  sequence.
- **A `const` used only in a type position fails
  `@typescript-eslint/no-unused-vars`** ("assigned a value but only used as a
  type"). In a `*.test-d.ts` that is the normal shape. Use an instantiation
  expression in the type query instead —
  `Static<ReturnType<typeof paginatedResponse<typeof Schema>>>` — which needs
  no binding at all.

## Reuse a shared TypeBox primitive with a field-specific description by SPREAD

Every remaining schema in both contract packages reuses `Timestamp`,
`MonetaryAmount` and `CurrencyCode`, and each usually wants to say what the
field means rather than what the type is. The two obvious routes are both
wrong:

- `Type.Ref(Timestamp, {...})` emits a `$ref` to a component that does not
  exist. The shared scalars deliberately carry no `$id` (a component per string
  type), so nothing hoists them and the reference dangles.
- Re-declaring `Type.String({ format: 'date-time', ... })` at the field drifts
  from the shared schema silently — no gate compares the two.

`{ ...Timestamp, description: 'field-specific' }` is the one that works.
Measured on `@sinclair/typebox@0.34.52`: object spread copies TypeBox's own
`Symbol(TypeBox.Kind)`, so the result is still a `TSchema`, `Type.Optional`
accepts it, `Static<>` still resolves, and the emitted JSON keeps `format` and
`examples` while taking the new `description`. Pair it with a case asserting
the inherited annotation survived (`format` here) — a hand-written copy passes
every other assertion in the file, and the leg that proves the difference is
replacing the spread with a literal `Type.String`.

## The contract-authoring conventions company.ts and card.ts set

Three decisions the remaining schema tasks (`transaction.ts`, `dashboard.ts`,
`contracts-service-b/invoice.ts`) should follow rather than re-derive, each
already argued in the module it lands in:

- **An identifier is an opaque bounded string, with no `format` and no
  `pattern`.** The columns are `uuid` today; publishing `format: 'uuid'` would
  make migrating off it a contract change — the same argument `MonetaryAmount`
  makes for stating no ceiling over a 32-bit column. `minLength: 1` plus a
  `maxLength` is a defensive bound on request-borne input, not a format claim,
  and it is stated **per identifier** rather than factored into one shared
  schema: two ids are two contract decisions, and one component is how
  loosening one silently loosens the other.
- **A contract enum is coarser than the database enum it maps from, and spelled
  differently.** `cards.lifecycle_status` has five members; `CardState` has four
  plus `unknown`, with `ordered`/`issued` folding onto `inactive` and
  `terminated` published as `closed`. Assert the divergence explicitly (the
  contract list must NOT contain the database's spellings) or a later
  well-meant "align the vocabularies" turns every column rename into a breaking
  change. That case is an absence, so it needs an inverting leg — adding the
  database spelling — to be worth anything.
- **Publish what the screen renders, and nothing more.** Removing a required
  response property is breaking and forces spec §6.2's major version; adding
  one is the additive change spec §6.1 lets a consumer author and ship the same
  day. So the cheap direction is the one to leave room in, and a field is left
  out until the screen asks for it. `CompanySummary` publishes 2 of the table's
  4 columns for that reason. A derived schema would publish all four because
  they happen to be there — the most concrete argument for spec §2.1 after the
  "field with no column at all" one.

Examples are aligned with `packages/db`'s seed (the seeded ids, `Company AB`,
`4321`) and spelled as literals rather than imported, since this package must
not depend on the db. Prism generates from `examples`, so matching them is what
makes the mock answer like a running `service-a` — the property spec §6.1's
unblocking workflow actually rests on.

## Lint a contract package's schemas against the house ruleset before emit

The "emitted document passes every house rule" test lands with the emit task,
several tasks after the schemas are authored, so a schema that fails gate 2 is
otherwise discovered late. The probe that closes the gap needs no contract and
no emitter: hoist each `$id`-carrying schema into `components.schemas` under
its id (deleting the `$id`, which is what `emitOpenApi` does), wrap them in a
minimal `openapi: 3.1.0` document with one operation carrying an `operationId`
and a 4xx `$ref`ing `#/components/schemas/Error`, and run
`vacuum spectral-report -r rulesets/house.spectral.yaml -o probe.json`.

Zero findings is only meaningful with the control beside it, for the reason
recorded above — a ruleset can report nothing forever. Mutating the probe
document (drop the enum's `unknown`, delete an `additionalProperties`) reported
`house-enum-has-unknown-member` and
`house-object-additional-properties-explicit`, which is what says the rules
read these schemas. Note `$ref` resolution
double-reported the second one, so read the codes and never a count.

## The spread idiom stops at `$id`, and gate 1 THROWS rather than warning

Bounds the "reuse a shared TypeBox primitive ... by SPREAD" note above, which
is true only for the scalars that carry no `$id`. `{ ...MonetaryAmount,
description: 'field-specific' }` produces a second schema carrying `$id:
'MonetaryAmount'` with different content, and `hoistComponent` in
`packages/contract-tooling/src/schemaRepresentation.ts` refuses it:

    emit gate cannot run: two different schemas, one of them at '<path>', both
    carry $id 'MonetaryAmount', so one would be published under the other's name

So the rule for any field reusing a hoisted object (`MonetaryAmount`, `Card`,
`CompanySummary`, `Transaction`, `PageInfo`, `Error`): pass the schema itself
and let it emit as a `$ref`. The field's meaning goes in the enclosing object's
docblock, not on the property. A `$ref` with a sibling `description` is legal
in OpenAPI 3.1, but TypeBox has no way to spell one without the spread that
causes the throw above.

The assertion that states the reuse, since a `$ref` is not visible in the
TypeBox JSON round trip: read the property's surviving `$id`
(`properties(X)['amount']?.['$id']` is `'MonetaryAmount'`). Comparing the
property against `emitted(MonetaryAmount)` states reuse too, but per the
convert-exactly-one-spelling note it then agrees with itself under any mutation
to the shared schema — that claim belongs to `shared.test.ts`. Proven by
mutation: replacing the reference with a hand-written inline copy reddens both
the reuse case and the full-shape case, by name.

## `$id` has a third case beyond "reused" and "scalar": an operation's response

`shared.ts` records two: objects reused across operations carry an `$id`,
scalars do not. Authoring `dashboard.ts` produced the third, and the remaining
contract modules should follow it rather than re-argue it:

- **An object an operation returns carries an `$id`**, even when one operation
  returns it. That name is what a consumer's generated client binds to and what
  the diff gate reports a change against.
- **An object that exists only inside one shape does not** — the scalar
  argument applied to a small object. `SpendSummary` is nested inside
  `Dashboard`, named by nothing else, and inlined; a component for it would put
  the two figures one indirection away from the field carrying them.

Both are worth a case, because neither is visible in a `Static<>` type — the
hoisted one asserts `emitted(X)['$id']` is `'X'`, the inlined one asserts
`emitted(Y)` has no `$id` property at all.

## `Type.Unsafe<T>`'s type parameter is invisible to every runtime assertion

The sharpest instance of the `*.test-d.ts` split, and it applies to every
contract enum in both packages, since `Type.Unsafe` is the repo idiom for one.
Measured on the transaction enums: changing `Type.Unsafe<MerchantCategory>` to
`Type.Unsafe<string>` emits **byte-identical JSON**, leaves all 86 runtime
cases green, and reddens only `transaction.test-d.ts`. The consumer loses its
union — the entire reason `Type.Unsafe` is used instead of a bare
`Type.String({ enum })` — and the four-gate order reports it in exactly one
place. Pin the union with `expectTypeOf<X>().toEqualTypeOf<'a' | ... |
'unknown'>()` per enum, or the `Type.Unsafe` choice is unenforced.

The mirror-image leg is worth keeping too: `Type.Union([Type.Literal(...)])`
leaves the TypeScript union intact and drops the `enum` keyword, so
`check-types` stays green and the JSON cases redden. Neither suite can make the
other's claim.

## zod 4 silently destroys `c.router()`'s types — do not call it, use `satisfies AppRouter`

The single most consequential finding for every remaining ts-rest task
(`contracts-service-b/src/contract.ts`, `service-a`'s routes, `service-b`'s
client, both `apps/web-*` clients). Measured on `@ts-rest/core@3.52.1` and
TypeScript 5.9.3, with controls in a throwaway workspace.

This repo's root `overrides.zod: 4.5.1` is a version ts-rest v3 was never typed
against — its declared peer is `zod: ^3.22.3`. Under zod 4, `c.router()` returns
a route type carrying an `[x: string]: any` index signature, so
`typeof contract.<route>` no longer satisfies `AppRoute` and every ts-rest
inference helper falls through to its *router* branch:

  ServerInferRequest<...>     -> { [x: string]: any; method: never; body: never }
  ClientInferResponseBody<...> -> any

Both are silent. A consumer pinning the package gets no types at all, and every
`expectTypeOf` assertion about them passes **vacuously** — `any` satisfies
`toEqualTypeOf` in both directions.

Controls, each run and each decisive:
  zod 3.25.76 + `c.router()` + zod schemas    -> correct types
  zod 3.25.76 + `c.router()` + `c.type<T>()`  -> correct types
  zod 4.5.1   + `c.router()` + either         -> degraded, as above
So it is the zod version, not TypeBox and not the adapter below.

**The fix is to skip `c.router()`.** A plain object literal closed with
`satisfies AppRouter` keeps every literal type and was verified to carry full
types through `initClient` *and* through `@ts-rest/express`'s
`initServer().router()` under zod 4 (`params`/`body` both inferred). What it
costs is the `commonResponses` router option, which an ordinary spread of a
shared `{ 401, 500 }` constant replaces. What it buys, beyond the types:

- `c.router()` is the only runtime import of `@ts-rest/core` a contract module
  needs, so dropping it makes the package's runtime graph **zod-free** — no
  `zod` dependency, contrary to the "@ts-rest/core's optional zod peer is a
  LIE" note above, which still holds for anything that *does* import it.
- ts-rest's `recursivelyApplyOptions` adds `headers: {}` to every route; without
  it `route.headers` is absent. Harmless on all three consumers checked:
  `emitOpenApi` returns no parameters for `undefined`, and `@ts-rest/express`
  runs `checkZodSchema(req.headers, undefined)` which short-circuits to success.

If a later task would rather have `c.router()` back, the other fix is changing
the root override to zod 3 and `contract-tooling`'s `zod: ^4.5.1` with it —
nothing in the repo imports zod, it is declared only to satisfy the peer.

## Handing a TypeBox schema to ts-rest: `contractSchema`, and why both halves need a suite

`packages/contracts-service-a/src/contract.ts` defines it and
`contracts-service-b` will need its own copy (six lines; two independently
versioned contract packages should not share a runtime helper):

    function contractSchema<Schema extends TSchema>(
      schema: Schema,
    ): ContractPlainType<Static<Schema>> {
      return schema as unknown as ContractPlainType<Static<Schema>>;
    }

ts-rest types every schema slot as `ContractAnyType` — a zod schema,
`c.type<T>()`'s opaque marker, or `null`. A TypeBox schema is none of them, so
passing one straight through is a `check-types` failure whose message names 46
missing zod members and points nowhere useful. `c.type<T>()` compiles and is a
bare symbol at runtime (gate 1 refuses it, reason `compile-time-type`). The cast
above is the only form that keeps the runtime schema *and* the consumer's type.

Because it is a cast, neither suite alone is evidence:

- `contract.test.ts` asserts the runtime value with `toBe` against the exported
  schema. Proven by six legs, each reddening exactly its predicted cases with
  the total holding at 18.
- `contract.test-d.ts` asserts `ClientInferResponseBody` / `ServerInferRequest`.
  Proven by six legs; the one that matters is rewriting the helper's return type
  to `ContractPlainType<unknown>`, which reddens 14 type cases and **zero**
  runtime cases.

One trap that cost a leg: `expectTypeOf<ServerInferRequest<R>['body']>()
.toEqualTypeOf<ActivateCardRequest>()` compares a derived type against the type
it is derived from, so renaming the field in the schema renames both sides and
the case stays green. Pin the shape literally as well
(`toEqualTypeOf<{ confirmedLastFour: string }>()`). Skill:
`convert-exactly-one-spelling`.

## OpenAPI ignores an `Authorization` header *parameter* — credentials are a securityScheme

Decided while authoring the contract, and it binds the emit-metadata task, both
`contracts-*` packages and `service-a`'s auth middleware. OpenAPI 3.x states
that a header parameter named `Authorization`, `Accept` or `Content-Type` SHALL
be ignored. So a route that declares one publishes a requirement no tool reads —
worse than declaring nothing, because it looks covered.

The contract therefore declares no credential header. What it states about
spec 2.3 is the `401` every operation carries; the credential itself belongs in
the emitted document's `securitySchemes`, supplied through `emitOpenApi`'s
`meta`. Note the spec wording is "a `client_id` **derived from** credentials" —
the consumer presents a credential and the provider resolves it, so `client_id`
is never a request field a consumer sends.

## `packages/contracts-service-a/src/contract.ts` is the published contract; import from `src/index.ts`

Four operations, flat router, keys are the operationIds `emitOpenApi` derives
and `api_usage` records: `listCompanies`, `getCompanyDashboard`,
`listCompanyTransactions`, `activateCard`. The module also owns the three shapes
that are an operation's own rather than a schema module's — `CompanyList`,
`TransactionList` and `ActivateCardRequest`, each carrying an `$id` per the
third case of the `$id` convention. All are re-exported from `src/index.ts`,
which is what `services/service-a`, `services/service-b` and both `apps/web-*`
should import.

Conventions it sets that `contracts-service-b` should follow rather than
re-derive, each argued in the module:

- **Error statuses are declared, never inferred.** `401` and `500` come from a
  spread of one `UNIVERSAL_FAILURES` constant; a route adds `400` where it takes
  input, `404` where it addresses something, `409` where state can conflict.
  No `403` (the catalogue folds "not yours to see" onto `not_found`) and no
  `429` (the catalogue has no code a consumer could branch on).
- **Every list is paginated, including the short one.** A list with no ceiling
  in the contract is an unbounded query in the provider.
- **A state change is a POST to a noun.** `POST /companies/:companyId/cards/
  :cardId/activation` answering `200` with the updated card, and `409` rather
  than a silent success on a second activation.

Verified end to end before commit, since the emit and house-rule tests land two
tasks later: `emitOpenApi` produces the four operations and ten components, and
`vacuum spectral-report` against the house ruleset reports **zero** findings.
Paired with five mutations of the emitted document — dropping an enum's
`unknown`, deleting an `additionalProperties`, dropping an `operationId`,
pointing an error response at a lookalike schema, making a field nullable —
each of which reported exactly its own rule code. A clean run without those is
indistinguishable from a ruleset that read nothing.

## A leaf's `scripts/` directory is linted but NOT type-checked until you say so

Every leaf tsconfig here sets `include: ["src", "*.ts"]`, which matches nothing
under a subdirectory other than `src`. eslint has no such notion and lints the
file regardless, so a build script lands half-gated: a style error fails `lint`
and a **type error passes every gate in the verification order**.

`packages/contracts-service-a/tsconfig.json` now reads
`["src", "scripts", "*.ts"]`. Any leaf that grows a `scripts/` directory —
`contracts-service-b` next — needs the same line, and the `**/*.test.ts`
exclude still applies inside it. Measured with negative controls on the new
file: `tsc --listFiles` names it, a `const x: string = 2` reddens
`check-types` with TS2322, a double-quoted string reddens `lint` with
`@stylistic/quotes`.

## The contract emit script: what it exports, and why the exports are the point

`packages/contracts-service-a/scripts/emit.ts` is the shape
`contracts-service-b`'s emit script should copy. It is wired to a per-package
`contracts:emit` script; there is deliberately no root fan-out, because
`scripts/pipeline-simulation.ts` is the thing that runs across every contract
package and it goes through `runGates`.

- It exports `buildDocument()`, `serializeDocument(document)` and
  `OPENAPI_DOCUMENT_PATH`, with the CLI behind the
  `fileURLToPath(import.meta.url) === process.argv[1]` guard so importing the
  module writes nothing (skill: `esm-dual-purpose-cli-module`; verified by
  importing it with the artifact deleted and confirming it stayed deleted).
  The byte-identity test lands two tasks later and has to re-emit through
  *these* exports — a test that rebuilds the metadata itself compares the
  committed artifact against its own copy of the same decisions, and stays
  green while the two drift apart.
- **`serializeDocument` is half of the contract with that test**: two-space
  JSON plus a trailing newline. Byte-identity is the entire reason to commit a
  generated file, so the formatting cannot be the test's private opinion.
- Every path resolves from `import.meta.url`, never `process.cwd()`. Verified
  by running the script from the repo root: same bytes, same destination, and
  no `openapi/` created at the root.
- **Three exit codes, the same split every gate here makes** — 0 written, 1
  gate 1 refused the contract (`UnrepresentableSchemaError`, reported with its
  `path` and `reason`), 2 the gate could not run. Both failure paths were
  driven rather than assumed: a prerelease `version` in the manifest gives 2, a
  `Type.Any()` planted in a schema gives 1 and names the offending path.

## What the emit metadata supplies, and the one block it deliberately omits

`emitOpenApi`'s `meta` is everything the emitted document states that the
contract itself does not. Two entries are governance decisions rather than
boilerplate, and the third is an omission worth stating:

- **`components.securitySchemes` is where the credential lives.** The contract
  declares no `Authorization` header parameter, because OpenAPI says a header
  parameter with that name SHALL be ignored — so without a scheme in the meta
  the emitted document states nothing at all about spec section 2.3. A
  scheme's `type: 'http'` trips neither house rule 2 nor 6: those key on
  `type == 'object'` and on a `type` **array** containing `null`.
- **`info.version` is read from the package manifest, never restated.** It is
  the number consumers pin (spec section 2.2) and the number the publish step
  names a baseline after. The script refuses anything that is not
  `<major>.<minor>.<patch>`, because `latestPublishedSpec` throws on a
  prerelease baseline — catching it at emit puts the refusal one step earlier,
  in front of the human still choosing the version.
- **No `servers` block.** A base URL says where a deployment lives, not what
  the API promises, and four callers read this one document. ts-rest clients
  take a `baseUrl` and Prism takes a host and port, so nothing needs it, and a
  hardcoded `localhost` in a published contract is a fact about one laptop.

Re-run the mutation controls after any metadata change, not only after a schema
change: the emitted document lints clean against the house ruleset, and clean
is indistinguishable from unread. Six mutations of the emitted JSON (drop an
enum's `unknown`, delete an `additionalProperties`, drop an `operationId`,
point a `401` at a lookalike error schema, make a field's `type` a
`["string","null"]` array, mark an operation `deprecated` with no `x-sunset`)
each reported exactly its own rule code and nothing else.

## A ranged workspace dependency still links, and `contract-` dodges the pin gate

`@marcos-corp/contract-tooling` is a **leaf devDependency** of a contract
package — build tooling, not published surface, the same exception as
`@types/express` and `drizzle-kit` — declared `^0.1.0` rather than pinned.
Measured: bun symlinks it into the leaf's own `node_modules` for a caret range
exactly as it does for an exact pin, so the "a bare exact pin already resolves
to the workspace package" note above holds in the range direction too.

Ranging it is correct rather than sloppy, and the reason is worth having ready
for a reviewer: `assertExactContractPins` governs the `@marcos-corp/contracts-`
prefix, and `contract-tooling` is singular `contract-`, one character short of
it. It is an ordinary internal library rather than a published contract, so it
carries no pinning obligation.

## Shell trap: cleaning up your own `mktemp -d` is refused too

Sharpens the `rm -rf` note above, which reads as being about a fixed
`/tmp/<name>` path. A trailing `rm -rf "$SCRATCH"` where `$SCRATCH` came from
`mktemp -d` is denied just the same, and the denial kills the **whole compound
command** — so the six mutation reports it was appended to never ran either,
and the failure looks like the probe rather than the cleanup. Leave the scratch
directory behind: `mktemp -d` is unique per run and nothing collides.

## The committed `openapi/` artifacts are read by NO lint gate — only the byte gate

Measured on `packages/contracts-service-a` the moment the artifacts landed, and
it holds for every `packages/contracts-*` package: the leaf
`eslint.config.mjs` ignores `openapi/**` and the root one ignores
`packages/**`, so `bunx eslint . -f json` in the leaf reads **27 files and
zero of them under `openapi/`**. `tsc` never saw them either — they are JSON.

So the two most reviewer-facing files in a contract package (`openapi.json` and
`openapi/published/<version>.json`) are outside `lint`, `lint:all` and
`check-types` entirely. The only gate that ever opens them is
`gate:control-bytes`, and that one scans **tracked** files, so a freshly
emitted artifact is read by nothing at all until it is committed.

Two consequences for the tasks that follow:

- **A green four-gate run after emitting is not evidence the document is
  well-formed.** Whatever check the artifact deserves — the house ruleset, the
  byte-identity test, a JSON parse — has to be run by hand in the same task, or
  written as a suite in the package (which is what the byte-identity task is
  for). Same shape as the "no lint gate reads YAML" note above.
- **Prose added under `openapi/` is unlinted**, unlike everything under
  `docs/`. A README there gets none of the markdown rules and none of
  `house/no-unsafe-unicode`. `latestPublishedSpec` ignores non-`.json` files,
  so such a README is safe to add; it is just ungated.

Worth pre-checking the artifact for what the byte gate will reject before
committing rather than after, since a rejection lands as a failed gate on a
generated file nobody edited: `JSON.stringify` escapes C0 bytes to `\uXXXX`, so
the realistic risk is only in prose the metadata carries. Both files here are
pure ASCII, 23230 bytes, zero non-ASCII code points.

## The FIRST published baseline makes gate 3 pass vacuously — invert it to read it

The publish step copies the working emit to
`openapi/published/<version>.json`, so on the day a baseline is first written
base and revision are the **same bytes** and `oasdiff` cannot report anything.
`runGates` says `diff: passed`, which reads as "the change is safe" and
actually means "there was no change". The same vacuity returns at every version
bump where the emit did not move, and at the CI publish step.

`skipped` versus `passed` distinguishes "no baseline published" from "a
baseline was compared", and that much is worth reading — but neither says the
gate can still fail. The pair that does, run against a scratch contract package
under `mktemp -d` (the shape recorded above: a `package.json`, one `src/*.ts`,
and `openapi/published/<v>.json`):

  baseline = the emit + one EXTRA required response property
      -> `diff: failed`, `dependency: not-run`, reasons naming
         `response-required-property-removed` and the operations it breaks
  same package, baseline deleted
      -> `diff: skipped`, `dependency: passed`

The direction is the thing to get right and is easy to invert: to make the
diff gate fire, the **baseline** must carry what the revision lacks. Adding a
field to the revision is the additive change spec §6.1 is built around and
reports nothing. Same asymmetry as the "removing an OPTIONAL response property
is not breaking" note above — the planted property has to be in `required`.

Note the second leg also proves the first is not passing for an unrelated
reason: the identical package with only the baseline removed changes the gate's
answer, so gate 3 is demonstrably reading that file and not resolving somewhere
else. Skills: `refusal-case-needs-a-positive-control`,
`accepting-cases-need-inverted-legs`.

## Emitting creates `openapi/` but not `openapi/published/` — mkdir before copying

Small and it will recur in `contracts-service-b`'s emit task, in the CI publish
step and in acceptance script 01. `scripts/emit.ts` does
`mkdirSync(dirname(OPENAPI_DOCUMENT_PATH))`, which is `openapi/` only. The
first baseline therefore needs `mkdir -p openapi/published` before the `cp`,
and a publish step that assumes the directory exists fails on exactly the run
that creates a package's first version.
