# Findings

## Workspace package layout (established by packages/db, reuse verbatim)

Every leaf workspace package carries five files and nothing else at setup time:

  <pkg>/package.json          name @marcos-corp/<x>, private, type module,
                              exports/main/types -> ./src/index.ts,
                              engines.node >=22, author + Apache-2.0 to match root
  <pkg>/tsconfig.json         extends ../../tsconfig.base.json; adds lib ES2022,
                              module ESNext, noUnusedLocals/Parameters,
                              noImplicitReturns/This, noFallthroughCasesInSwitch;
                              include ["src", "*.ts"];
                              exclude ["node_modules","dist",".tmp","drizzle","**/*.test.ts"]
  <pkg>/eslint.config.mjs     `import baseConfig from '../../eslint.base.mjs'`,
                              exports [ {ignores:[...]}, ...baseConfig ]
  <pkg>/vitest.config.ts      environment node, include ['src/**/*.test.ts']
  <pkg>/src/index.ts          module placeholder (`export {};`) until real exports land

Leaf scripts are exactly: `lint`: `eslint .`, `check-types`: `tsc --noEmit`,
`test`: `vitest run`. All three run from the package directory, so each picks up
its own leaf config with no extra flags.

## Tooling devDependencies stay at the ROOT, not in leaf packages

eslint, typescript, vitest, typescript-eslint, globals, jsonc-eslint-parser etc.
are already root devDependencies and hoist into the top-level node_modules, so
`bun run lint|check-types|test` inside a package resolves them without the
package declaring anything. Do NOT re-declare them per package — that is version
drift for no gain. Only declare a package's own *runtime* deps (drizzle-orm,
@sinclair/typebox, express, ...). The ported reference package under
.claude/worktrees/ duplicates devDeps because it was a standalone template; do
not copy that part of it.

## `--passWithNoTests` is temporary debt, not the convention

A package created before its first suite exists needs `vitest run
--passWithNoTests`, otherwise vitest exits 1 on "No test files found" and the
plan's "test:all exits 0 across all eight packages" task cannot pass. The flag is
recorded in that package's vitest.config.ts comment. **Drop the flag in the same
task that adds the package's first test file** — left in permanently, a deleted
suite goes green and unnoticed.

## bun does NOT symlink a workspace package into node_modules until something depends on it

`node_modules/@marcos-corp/` does not exist even after `bun install` registers
`packages/db` in bun.lock (verified: the ported reference monorepo has no
`node_modules/@ar` either, same setup). Consequence for any task wiring a
cross-package import: the consumer must declare the dependency in its own
package.json, or both `import/no-unresolved` and tsc will fail. Registering the
workspace is not enough.

## Root eslint leaf ignores `packages/**` but NOT `apps/**` or `services/**`

`eslint.config.mjs` at the root ignores only `packages/**`. When `apps/*` and
`services/*` land, root `bun run lint` will lint them with the ROOT config
(whose import resolver points at `./tsconfig.json`, which excludes them), and
`lint:all` will then lint them a second time through their own leaf config. The
task that creates the first app or service must add `'apps/**'` and
`'services/**'` to the root ignores block.

## Prove a green gate actually read the files

`eslint .` exiting 0 proves nothing on its own. Two cheap checks used here:
  bunx eslint . -f json | ...        -> count + names of files actually linted
  bunx tsc --noEmit --listFiles      -> the exact file set tsc type-checked
and a throwaway violation file (e.g. a double-quoted string) to confirm the gate
reddens before deleting it. Worth repeating for each new package.

## Shell traps hit in this repo

- The Bash tool's cwd PERSISTS between calls. A `cd packages/db` in one call
  makes a relative `cd packages/db` in the next call fail. Use absolute paths.
- The shell is zsh: `${PIPESTATUS[1]}` after a pipe reads the WRONG element and
  a trailing `; echo $?` after a pipe reports the exit of the LAST stage (often
  `tail`/`ls`), not the command under test. Capture with
  `cmd > /tmp/x.log 2>&1; echo "EXIT=$?"` when the exit code is the evidence.

## Verification order (from AGENTS.md), all four confirmed green with packages/db

  bun run lint && bun run check-types && bun run test && bun run gate:control-bytes

`gate:control-bytes` scans **tracked** files only, so a new package is outside
its scope until it is committed — run it once more after the commit.

## Cloning the packages/db layout: two bits are db-specific, drop them

`packages/db` is the template for every remaining leaf, but two of its lines
describe drizzle artifacts and mean nothing anywhere else:

  tsconfig.json   exclude ["...", "drizzle", ...]   <- drop outside packages/db
  eslint.config.mjs  { ignores: ['drizzle/**', ...] } <- drop outside packages/db

Keep `.tmp/**` in both; it is generic. Copying `drizzle` into a package that
will never hold a migration reads as cargo-cult to the reviewer. Everything
else in the five-file layout transfers verbatim.

## What each leaf gate actually reads (measured, not assumed)

In a leaf package, `eslint .` and `tsc --noEmit` cover DIFFERENT file sets:

  eslint .        5 files: eslint.config.mjs, vitest.config.ts, src/index.ts,
                  AND package.json + tsconfig.json (the jsonc plugin in
                  eslint.base.mjs makes both JSON configs real lint targets)
  tsc --noEmit    2 files: src/index.ts, vitest.config.ts
                  eslint.config.mjs is NOT type-checked (.mjs, allowJs off)

Two consequences: a badly formatted package.json fails `lint`, not
`check-types`; and a type error inside a leaf `eslint.config.mjs` is invisible
to every gate in the verification order.

## bun uses the ISOLATED linker: a leaf's runtime deps are NOT hoisted to root

The devDependency note above is true only for the ROOT. A dep declared by a
leaf is symlinked into `packages/<pkg>/node_modules/` and never appears in the
top-level `node_modules/` (real copies sit under `node_modules/.bun/`).
Verified with @sinclair/typebox and @ts-rest/core.

- Leaf runtime deps resolve for `lint`/`check-types` only because those scripts
  run FROM the package dir. Never "fix" a leaf import by adding the dep at root.
- `ls node_modules | grep <dep>` at the root is a false-negative install check;
  read `packages/<pkg>/node_modules/`, or `node_modules/.bun/`, which carries
  the resolved version in the directory name.

## @ts-rest/core peers zod OPTIONALLY, so the root zod override is not a conflict

`@ts-rest/core@3.52.1` (the `latest` tag; there is no v4) declares
`peerDependencies.zod: ^3.22.3`, which looks like a clash with root
`overrides.zod: 4.5.1`. It is not — `peerDependenciesMeta` marks zod and
@types/node **optional**, and zod is not installed at all. Check
`npm view <pkg> peerDependenciesMeta` before working around a peer warning.

## Prove a new dependency resolves, with a negative control

Gates stay green whether or not a declared dep is importable, so declaring one
and re-running them proves nothing. Per package that adds a runtime dep:
write `src/__probe.ts` importing it and using a real export; `bunx tsc
--noEmit` and `bunx eslint src/__probe.ts` must both exit 0 (eslint's
`import/no-unresolved` covers what tsc does not); then break it deliberately
(type error, then an import of a nonexistent package) and confirm each gate
exits non-zero; then delete the probe and re-run. Without the negative control
a green run is indistinguishable from a gate that read nothing.

## Two deltas specific to `packages/contracts-*`

- Leaf `eslint.config.mjs` must ignore `openapi/**`: those packages commit
  emitted `openapi/openapi.json` and `openapi/published/<version>.json`, and
  the jsonc plugin in `eslint.base.mjs` makes every committed .json a lint
  target otherwise.
- The manifest `version` is API surface, not bookkeeping — consumers pin it
  exactly with no range specifier (spec 2.2) and a gate enforces that, so
  bumping it is the reviewable event. The packages still stay `private: true`;
  "published" here means the committed OpenAPI document, never an npm registry.

## For a "mirror package X" task, diff the configs instead of re-reading them

Several plan tasks say "mirroring the <other> package configuration"
(contracts-service-b, service-b, web-a/web-b). After writing the new leaf, run
`diff <template>/<file> <new>/<file>` for each of package.json, tsconfig.json,
eslint.config.mjs and vitest.config.ts. A faithful mirror produces only the
name / display / description lines; anything else in the diff is an unintended
delta. This is stronger than re-reading each file, and it catches the reverse
failure too — a template-specific line copied where it does not belong (see the
drizzle-exclude note above).

## The root eslint ignores block is now closed over all three workspace globs

Confirmed by measurement, not assumption: with `services/` present and only
`packages/**` ignored, root `eslint .` read 32 files including all five
service leaf files; after adding `'apps/**'` and `'services/**'` it read 27 and
none under apps/ or services/. The root `eslint.config.mjs` ignores block now
lists all three globs declared in `package.json` workspaces, so no later
`apps/*` or `services/*` package has to touch it again. Root `tsconfig.json`
never needed the same fix — its `include` is `["tools", "*.ts", "*.mjs"]`, so
leaf packages were already outside it.

## ts-rest v3 pins Express 4, and its express peer is NOT optional

`@ts-rest/express@3.52.1` (the `latest` tag; 3.53.x is alpha/rc only) declares
`peerDependencies: { "@ts-rest/core": "~3.52.0", "express": "^4.0.0", "zod":
"^3.22.3" }` with **only zod** marked optional. Express 5.2.1 is `latest` on npm
and does not satisfy `^4.0.0`. Any service in this repo therefore takes
`express@^4.22.2` with `@types/express@^4.17.25`, and must also declare
`@ts-rest/core` itself — a non-optional peer does not get resolved for you under
bun's isolated linker. `bun install` printed no peer warnings with that set,
which is the check worth reading.

`@types/express` belongs in the **leaf** devDependencies, not the root: it is
package-specific typing rather than shared tooling, and the isolated linker
requires it to resolve from the package directory. That is the exception to the
"tooling devDeps stay at the root" note above — the rule is about *shared*
tooling, not about the `devDependencies` field.

Unrelated aside worth knowing: `@ts-rest/express`'s .d.ts references
`z.ZodObject` even though zod is not installed. `skipLibCheck: true` in
`tsconfig.base.json` is what keeps that from failing `check-types`.

## Proving a `dev` script, which by design never exits

`bun --watch <entry>` stays resident, so `bun run dev; echo $?` hangs rather
than reporting. Two cheap readings instead:
  bun src/index.ts                          -> entrypoint executes, exit 0
  bun run dev (backgrounded) + pgrep -fl    -> the script resolves and the
                                               watcher is actually running
then `pkill -f 'bun --watch src/index.ts'`. The backgrounded job reports exit
143 (SIGTERM) afterwards; that is the kill, not a failure.

## A service leaf carries a `dev` script; the entrypoint is src/index.ts

`src/index.ts` is already the package's `exports`/`main`/`types`, so pointing
`dev` at it keeps one entrypoint and makes the script runnable from the day the
package is created rather than pointing at a `server.ts` that lands tasks later.
When `server.ts` arrives, wire it in through `src/index.ts` instead of
repointing the script.

## `bun install` printing "no changes" still registers a new workspace package

Adding a leaf whose runtime deps are already in the lockfile (a mirror of an
existing package) makes `bun install` print `Checked N installs across M
packages (no changes)`. That line describes the *dependency graph*, not the
workspace set, and reads as a no-op when it is not one — the same run wrote
`Saved lockfile`, added the `services/<pkg>` / `@marcos-corp/<pkg>` entries to
`bun.lock`, and created the leaf's own `node_modules/` symlinks. Do not re-run
install or start debugging on the strength of "no changes"; read the two things
that actually answer it:

  grep '<pkg>' bun.lock              -> workspace entry + resolution line
  ls <pkg>/node_modules              -> the isolated linker's per-leaf symlinks

## A dependency-free leaf gets NO `<pkg>/node_modules` at all

Refines the two notes above about the isolated linker. `ls <pkg>/node_modules`
only answers "did the leaf's own runtime deps link"; for a leaf that declares
none (apps/web-a, apps/web-b, packages/db, packages/contract-tooling) the
directory is never created, so its absence reads as a failed install when
nothing is wrong. To confirm a workspace registered, read `bun.lock` — both the
`"<glob>/<pkg>": { "name": "@marcos-corp/<pkg>" }` workspace entry and the
`"@marcos-corp/<pkg>": ["@marcos-corp/<pkg>@workspace:<glob>/<pkg>"]`
resolution line — and confirm the package appears in the
`bun run --filter '@marcos-corp/*' <script>` output. Such a leaf still lints,
type-checks and tests green because every tool it uses is a hoisted root
devDependency.

## `bun run --filter` DOES propagate a leaf failure — verified, not assumed

A green `bun run <gate>:all` is otherwise indistinguishable from a `--filter`
that swallows leaf exit codes, and every "all N packages exit 0" claim in this
plan rests on it. Measured by planting one violation in a single leaf and
reading the aggregate exit:

  lint        double-quoted string   -> leaf 1, aggregate 1
  check-types `number` into `string` -> leaf 2, aggregate 2  (tsc's 2 shows through)
  test        `expect(1).toBe(2)`    -> leaf 1, aggregate 1

Two properties worth knowing beyond the propagation itself:

- It does **not** short-circuit. The other seven leaves still ran and still
  printed `Exited with code 0` in the same failing capture, so the presence of
  green lines next to a red one is normal output, not a partial run.
- The aggregate takes the leaf's own code, so a non-1 exit (tsc's 2) is a real
  reading, not a harness artifact. Test for non-zero, never for `-eq 1`.
- Leaf order is **nondeterministic** between runs. Never read the Nth line
  positionally; `grep -oE '@marcos-corp/[a-z-]+ <script>: Exited with code 0'`
  and `sort` before comparing two captures or counting the package set.

Re-do the plant/restore control whenever a new gate script is added to the root
`*:all` fan-out. It costs three runs and is the only thing separating "eight
packages pass" from "the filter reported nothing eight times".

## The `packageManager` pin is NOT enforced by bun

`package.json` pins `bun@1.3.9`; `bun install` ran as **1.3.14** and said
nothing. Unlike corepack-managed pnpm/yarn, bun does not refuse or self-switch
on a mismatched `packageManager` field, so that line documents intent only. Read
`bun --version` when a version-sensitive behaviour is in question rather than
trusting the manifest, and expect CI's bun to differ from the local one unless
the workflow pins it explicitly with `oven-sh/setup-bun`.

## A green `test:all` currently proves nothing about the eight leaves

Extends the `--passWithNoTests` note above with the measured state: all eight
leaf packages carry the flag and all eight print `No test files found, exiting
with code 0`. Every one of the 45 passing tests belongs to the ROOT suite over
`tools/`. So `test:all` exiting 0 is a statement about the root plus eight
no-ops. Any later task claiming coverage from a leaf must read that leaf's own
`Test Files N passed` line, not the aggregate exit — and should drop that leaf's
`--passWithNoTests` in the same commit that adds its first suite.

## No lint gate reads YAML or extensionless files -- only the byte gate does

`eslint.base.mjs` declares `files:` for js/mjs/cjs/ts/tsx/jsx/md/json and
nothing else. So `.github/CODEOWNERS`, `.github/workflows/*.yml`,
`docker/compose.yaml` and `packages/contract-tooling/rulesets/*.yaml` are
outside `lint`, `lint:all` and `check-types` entirely. The only gate that ever
opens them is `gate:control-bytes`, and that one scans **tracked** files, so a
brand-new YAML or extensionless config is read by nothing at all until it is
committed. A green four-gate run after adding one is not evidence the file is
well-formed -- whatever validity check that file deserves has to be written or
run by hand in the same task.

## A path-pattern config that matches nothing fails silently -- check it, with a control

CODEOWNERS, workflow `paths:` filters and ruleset globs all share the failure
mode: a typo'd or wrong-case path is not an error, it just owns/triggers
nothing, and the file still reads as correct. Cheap check that catches it --
for every non-comment rule, count the tracked files the pattern actually
matches:

  grep -vE '^\s*(#|$)' <file> | while read -r pat rest; do
    printf '%-34s %s\n' "$pat" "$(git ls-files -- "${pat#/}" | wc -l)"
  done

Pair it with a negative control in the same run (a nonexistent sibling, a
misspelling, a case variant) or a check that reports a nonzero count for
everything is indistinguishable from one that works. Both were run for
`.github/CODEOWNERS`: 8 rules x 5 tracked files each, 0 for all three controls.

## CODEOWNERS semantics that the plan's prose does not imply

Relevant to `docs/ownership.md`, the CI `paths:` filters and acceptance script
05, all of which reason about who approves what:

- **Last match wins.** Ownership does NOT accumulate across matching lines the
  way .gitignore rules do; the final matching rule is the only one that applies.
  List general patterns before specific ones.
- **A leading `/` anchors to the repo root.** `packages/db/` without it also
  matches any nested `packages/db/` deeper in the tree.
- **Two owners on one line means EITHER may approve**, not both. To require two
  approvals you need the PR to touch two paths with disjoint owner sets.
- **An unresolvable handle matches nobody, with no error.** The org/team form
  `@marcos-corp/team-a` cannot resolve on a user-account repo like this one, so
  every rule here is documentation until the handles are swapped (tracked in
  `.plans/PREREQUISITES-*.md`) and branch protection on `main` requires
  code-owner review.

## Tracked markdown IS a lint target -- `docs/**` is not ignored anywhere

Refines the "no lint gate reads YAML or extensionless files" note above: the
opposite is true for `.md`. `eslint.base.mjs` declares a `files: ['**/*.md']`
block extending `markdown/recommended`, and the root `eslint.config.mjs`
ignores block lists only the three workspace globs plus `.claude/`, `.plans/`,
`.specs/`, `.tmp/`, `.docs/` -- **not** `docs/`. So every file added under
`docs/` is read by root `bun run lint`, and by `gate:control-bytes` once
committed.

Measured, with negative controls, when `docs/ownership.md` landed:
  bunx eslint . -f json | ...      -> 28 files, docs/ownership.md among them
  `#BadHeading` planted            -> exit 1, markdown/no-missing-atx-heading-space
  literal U+200B planted           -> exit 1, house/no-unsafe-unicode
  restored                         -> exit 0
  gate:control-bytes               -> 93 files pre-commit, 94 after

Rules that actually bite prose: `no-missing-atx-heading-space`,
`no-duplicate-headings`, `no-multiple-h1`, `table-column-count` (every row of a
table needs the same cell count). `markdown/no-missing-label-refs` is turned
off in `eslint.base.mjs`, so bare `[bracketed]` text is safe.

Related skills for the remaining `docs/*` tasks:
`markdown-link-check-strip-code-regions` (strip fences/spans before scanning
for links) and `wrapped-prose-edit-safety` (span edits never reflow the rest of
a hand-wrapped paragraph).

## Width checks with awk count BYTES, so `--` and section signs read as over-long

Prose convention in this repo's authored docs (AGENTS.md, CLAUDE.md, `.specs/`,
`.plans/`) is hand-wrapped at 80 columns; tables and long link targets are
allowed past it. README.md and PRESENTATION.md are unwrapped and are not the
model to copy.

`awk '{ if (length($0) > 80) ... }'` on macOS counts bytes, not characters. An
em dash costs 3 bytes and a section sign 2, so a correctly wrapped 80-character
line reports as 85 and reads as a violation that is not there. Subtract the
multibyte characters before believing the number, or measure with
`python3 -c "print(max(len(l) for l in open(p)))"`.

Neither character is banned -- `house/no-unsafe-unicode` flags only C0/DEL,
BiDi overrides, zero-width and default-ignorable code points, and U+2028/9. The
existing docs use both.

## Relative links out of `docs/` resolve, and are worth checking with a control

A link from `docs/x.md` to a repo-root path needs the `../` prefix
(`../.github/CODEOWNERS`), and nothing in the four-gate verification order
opens it -- a dead link is green. Cheap check, run from the repo root:

  grep -oE '\]\(([^)]+)\)' docs/x.md | sed 's/](//; s/)$//' | while read -r l; do
    python3 -c "import os,sys; p=os.path.normpath('docs/'+sys.argv[1]); \
      print(('OK      ' if os.path.exists(p) else 'MISSING ')+p)" "$l"
  done

Pair it with a deliberately misspelled target in the same run, or a checker
that reports OK for everything is indistinguishable from one that works.

## Docs that describe not-yet-built code: bound the staleness, don't scatter it

Every remaining `docs/*` task writes prose about gates, scripts and workflows
that land in later stages. Two rules keep those docs from being silently
falsified by the commit that builds the thing they describe:

- **Reference a file that does not exist yet in backticks, never as a markdown
  link.** `docs/ci.md` in backticks is a forward pointer; `[x](ci.md)` is a dead
  link that the four-gate order will never catch (nothing in lint, check-types,
  test or the byte gate opens a link target).
- **Confine "not true yet" claims to one clearly-titled section, and phrase each
  so it is still true at the end of the plan.** "The CODEOWNERS handles are
  placeholders" and "the 13-month retention is a requirement this PoC does not
  satisfy" survive every later stage. "These gates do not exist yet" does not,
  and goes stale in a file nobody re-reads. See `stale-prose-sweep-on-commit`.

## Where the governance facts live, so docs tasks stop re-deriving them

`docs/governance.md` is now the single place the spec §10 decisions are recorded
as resolved (TypeBox + ts-rest in contract packages, Zod everywhere internal but
never in `packages/contracts-*`, `client_id` issued manually with a named owner,
contract packages versioned independently). Later docs, README sections and
package `AGENTS.md` files should link to it rather than restating the rationale.

The spec sections each doc task draws from, since they are not adjacent in the
file: §4 tier-to-gate table, §7 out-of-scope triggers, §8 gate order + house
rules, §9 acceptance criteria, §10 open decisions. `PRESENTATION.md` lines 18-56
hold the original tier definitions that §4 restates.

## Checking a markdown table before lint does: count cells per row

`markdown/table-column-count` fires on a row whose cell count differs from the
header, and a hand-aligned table is easy to get wrong mid-edit. Cheaper than
reading it: strip the leading/trailing pipe, split on `|`, and assert one
distinct count per contiguous table block. Run it together with the h1-count and
duplicate-heading checks — all three are pure text and need no tooling.

## vacuum is Spectral-*ruleset* compatible, not Spectral-*function* compatible

Measured on vacuum 0.30.3 while authoring
`packages/contract-tooling/rulesets/house.spectral.yaml`. Each item below turns
a rule into a silent pass: it loads, it counts toward "containing N rules", and
it reports nothing, ever.

- The `schema` function only validates a **`field`**, never the `given` node.
  Spectral's node-level `then: {function: schema}` with no `field` checks
  nothing. This is the easiest way to ship a dead rule.
- With a `field`, `schema` still passes when that field is **absent** unless
  `forceValidation: true` is set.
- `functionOptions` rejects Spectral's `allErrors`, and surfaces the rejection
  as a *violation on the spec* ("property 'allErrors' is not a valid property
  for 'schema'") rather than as a ruleset load error.
- `message:` is **not** interpolated -- `{{path}}` / `{{property}}` / `{{error}}`
  print literally. Reported text is `"<description>: <function message>"`, so
  write `description` to read as the first half of that sentence and omit
  `message`.
- `@property` is unsupported in filters, so "every 4xx/5xx response" must be an
  explicit union: `responses[400,401,403,404,409,422,500]`.

What does work and is worth reaching for: filters support `!`, `&&`, `||`, `==`
and nested member access (`$..[?(@.items && !@.items.type)].items`); `then`
accepts an **array** of entries against one `given`; the schema function
supports `patternProperties`, `contains`, `const` and `not`. Prefer the
given-as-predicate idiom -- select only the offending nodes, then assert
something that cannot hold -- over a node-level schema check: it yields real
document paths and messages like "`type` must be defined".

## vacuum resolves $ref before running a rule, which changes what a rule can see

Default execution is against the **resolved** document, so a `$ref` string is
already gone; a rule reasoning about one needs `resolved: false` on that rule.
Two consequences past that:

- One violation can be reported **twice** -- once at its real path, once at the
  resolved copy, where vacuum cannot render a path and prints the raw filter
  (`[?(@.type == 'object')]`) instead. Assert the rule **code**, never a finding
  count of exactly 1.
- `range.start.line` is correct even when the path is that raw filter, so it is
  the field to point a human at.

## Reading vacuum from code: `lint` has no JSON, and `spectral-report` has THREE outcomes

`vacuum lint` exits 0 clean / 1 at error severity but has no JSON flag. The
machine-readable path is `vacuum spectral-report -r <ruleset> -o <spec>`, which
writes a bare JSON array to stdout with no banner and **exits 0 whether or not
there are findings**. Anything shelling out to it must derive pass/fail from the
parsed array, not from the exit code. Finding fields: `code` (rule id), `path`
(array), `message`, `severity`, `range.start.line`. Both YAML and JSON specs
work, so the committed `openapi/*.json` artifacts lint directly.

The exit-0 rule holds only while the spec **parses**. There is a third outcome,
and it is the one that breaks a naive wrapper: on an unparseable spec vacuum
exits **2** and writes an ANSI-coloured `✗ Failed to parse specification '<path>'`
to **stdout**, not stderr. So `JSON.parse(stdout)` throws rather than returning
an empty finding list, and the throw does not name the spec unless the raw
stdout is kept. Any `lintSpec` has to branch on all three: exit 2 (unparseable,
report the path), exit 0 with `[]` (clean), exit 0 with findings (fail). Note
the blob carries ESC bytes, so never tee it into a tracked file -- that is
exactly what `gate:control-bytes` and `house/no-unsafe-unicode` reject.

vacuum is a documented prerequisite and is **not** installed on this machine.
For local verification without touching the repo:
`npm install --prefix /tmp/vacuum-probe @quobix/vacuum@0.30.3`, then prepend
`/tmp/vacuum-probe/node_modules/.bin` to PATH. Pin the version CI installs.

## Prove a lint rule is live: one violating document per rule, and per leg

A ruleset that loads and reports nothing looks exactly like a correct one. What
separates them, and the shape `fixtures/` needs: one document per rule violating
exactly that rule, one satisfying every rule, then assert the **set of rule
codes** each produces. Two legs that are easy to skip and were both needed here:

- Every entry of a multi-path `given` needs its own hit. A document planting the
  same violation at each covered position proves all of them at once; one that
  only exercises `components.schemas[*]` leaves the other paths unproven.
- Every entry of a `then` array needs its own violating case. The sunset rule's
  `pattern` leg (a malformed `x-sunset`) never runs against a fixture that only
  omits the field.

Also worth a tolerance case per rule, not just a violation: the typeless-schema
rule must **not** fire on an `anyOf`/`enum` schema that legitimately carries no
`type`, and the null rule must not fire on `nullable: false`.

## The house-rule fixtures exist now: `fixtures/<valid|violations>/`, keyed by filename

`packages/contract-tooling/fixtures/` is the shared test data for the house
ruleset, and every later gate task (`lint.ts`, `gates.ts`, the integration test,
`pipeline-simulation`) should consume it rather than inlining its own spec
strings. The contract downstream code depends on:

- `violations/<rule-code>[.<leg>].yaml` must report `<rule-code>` and no other
  code. **The expected code is the filename up to its first `.`**, so a suite
  derives expectations instead of carrying a table that drifts when a rule is
  added. The optional `.<leg>` segment names which `then` entry it exercises.
- `valid/satisfies-all-rules.yaml` must report nothing.
- Six rules, nine violation documents -- rules 4, 5 and 6 each carry a two-entry
  `then`, and each entry needs its own document.

Two closure checks worth re-running whenever a rule is added, both cheap and
both catching a failure that is otherwise silent: no rule in the ruleset lacks a
fixture, and no fixture names a rule that does not exist. A fixture whose name
no longer matches a renamed rule still passes its own assertion.

Assert the **set** of distinct codes, never a finding count: `$ref` resolution
double-reports a violation on a referenced schema (measured: 1 planted breach on
a `$ref`d schema -> 2 findings), so `toHaveLength(1)` is flaky by construction.

## A mutation control that silently tests an EMPTY file instead of a mutation

Bit me while proving these fixtures discriminate, and it is invisible because
the control still reports the failure it was supposed to report -- for entirely
the wrong reason. In Python, `open(p,'w')` is evaluated **before** the argument
expression, so

    open(p,'w').write(open(p).read().replace(a, b))   # WRONG - wipes the file

truncates `p` to zero bytes and then reads the now-empty file. The "mutated"
fixture is an empty file. A linter/parser then fails on it, the control prints
the expected FAIL, and nothing about the run says the mutation never applied.
Same trap in shell: `cmd < f > f` and `sed ... f > f` truncate before reading.

Read first, write second, and assert the edit changed something:

    src = open(p).read()
    out = src.replace(a, b)
    assert out != src, 'mutation did not apply'
    open(q, 'w').write(out)

The `assert out != src` is the load-bearing line -- it is what separates a
control that mutated the file from one whose search string silently missed. Do
the mutation on a copy under /tmp, never in the tracked tree.
